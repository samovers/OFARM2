# Operation claim writer inside the tenant transaction

Phase A for [#422](https://github.com/samovers/OFARM2/issues/422). The primary trust boundary is **assertion-domain validation and writing**. [#178](https://github.com/samovers/OFARM2/issues/178) calls this writer through the [tenant transaction guard](https://github.com/samovers/OFARM2/issues/424).

## What a successful return means

A new, admitted `ASSERT_OPERATION_CLAIM` attempt can stage exactly one immutable `OPERATION_CLAIM_ASSERTION` with `claimState = PENDING_REVIEW`. The protected assets are the assertion, its validation evidence and the existing records it refers to. The writer returns while the caller still owns the transaction. At that point the caller can read the staged bytes and can still roll back the entire write.

1. **#178 identifies a new eligible attempt.** It checks the saved operation under its concurrency guard, binds the original intent and supplies the selected authorization, assertion-act evidence, applicable gate evidence and protected inputs. The selected rule and guards must cover this action, tenant, attempt, result ID and exact proposed bytes. A completed operation goes directly to #178's saved-result path. [Successful call order](https://github.com/samovers/OFARM/blob/b1abe2c93c7ca8b7a94a11bdb0fded64bb2e75e6/package_meta/history/clean_baseline_migration/phase_reports/not_required_transaction_and_consumption_protocol_rfc_candidate_v0_1.md#L651)
2. **#422 maps and validates the assertion.** Copy the proposed stable ID from the authorized effect subject. Derive the asserting Party from the selected authority path and preserve the alleged performer's distinct provenance. Verify the original assertion time, subject, scope, body and evidence against their selected immutable sources. Validate all applicable contract mappings and postconditions, including the guarded absence of a conflicting result. A domain refusal stages no successful assertion or validation evidence. [Claim mapping](https://github.com/samovers/OFARM/blob/b1abe2c93c7ca8b7a94a11bdb0fded64bb2e75e6/package_meta/history/clean_baseline_migration/phase_reports/not_required_transaction_and_consumption_protocol_rfc_candidate_v0_1.md#L1199) · [Domain validation](https://github.com/samovers/OFARM/blob/6c5c6eb754baecfa38b7e364fc3d0318ae1ad89f/package_meta/history/clean_baseline_migration/phase_reports/assertion_record_submission_protected_effect_contract_rfc_candidate_v0_1.md#L602)
3. **#422 stages the validated bytes and their evidence.** Use a claim-specific operation bound to the caller's existing tenant, PostgreSQL transaction and governed batch. Return the assertion ID, schema binding, digest of the complete canonical assertion, protected-effect contract binding and passing validation-trace reference and digest. The assertion, trace and trace's domain payload must all be resolvable in this transaction. The payload binds the actual inputs, mappings and postconditions. A second connection, a caller-supplied verdict or a trace constructed from unverified bytes cannot satisfy this interface. [Required result binding](https://github.com/samovers/OFARM/blob/b1abe2c93c7ca8b7a94a11bdb0fded64bb2e75e6/package_meta/history/clean_baseline_migration/phase_reports/not_required_transaction_and_consumption_protocol_rfc_candidate_v0_1.md#L396)
4. **#178 verifies the return and owns finalization.** It verifies the bytes and references, adds the original operation result, consumption and receipt under its own contract, and commits or rolls back. A caught failure after the write operation begins must leave the tenant transaction rollback-only. A normal exit after such a failure reports `TRANSACTION_FAILED`. Commit with uncertain acknowledgement follows the transaction owner's reconciliation path. #178 recovers an exact retry and consults the current disclosure authority before releasing a saved result. The pending claim creates no review decision, accepted consequence or current-state change. [Failure handling on main](../../kernel/tenant_uow.py) · [Atomic outcome](https://github.com/samovers/OFARM/blob/b1abe2c93c7ca8b7a94a11bdb0fded64bb2e75e6/package_meta/history/clean_baseline_migration/phase_reports/not_required_transaction_and_consumption_protocol_rfc_candidate_v0_1.md#L678)

## Authority and storage

The primary risk is that an unverified or partial claim becomes durable under another attempt. Contain it by validating the authorized ID and exact bytes against trusted inputs, staging the assertion and its evidence through the transaction-bound operation, and requiring the original transaction to commit the complete set together. A caught error after staging makes that transaction rollback-only.

The caller can supply proposed content. Trusted producers supply the authorized Party, assertion act, selected schemas and protected source state. The design assumes an uncompromised database, deployed application and separately admitted producers. A caller-supplied gate result cannot create a passing trace.

The production Commit Ingress trace operation is still required. The legacy M1 emitter is isolated. The v0.1 trace requires a semantic-event reference and primary family. For a claim with no associated event, the ingress owner must supply a separately governed submission event or an approved compatible trace representation. The writer cannot derive a family from the operation-claim subtype. #178 must bind that ingress trace as permitted gate evidence in its complete success set. ## PostgreSQL acceptance

Use the production writer under the tenant role, with real selected inputs and the same backend throughout the call. Start each case with a distinct admitted claim ID and attempt. Use a fresh, authorized observer transaction after each outcome and show that it can read a known committed record and its evidence for the same tenant. For commit, #178 invokes Kernel Commit Ingress to stage the trace and its link and completes the other required members of the transaction. Count all new assertion and evidence rows for the attempt and follow the returned references as well. Counting just the expected ID could miss a duplicate with a different ID. Pre-existing source evidence must survive each case.

| Case | Observation required |
| --- | --- |
| Rollback after return | In the writing transaction, resolve the returned ID, validation trace and domain payload. A separate connection sees none of these new rows. Force the caller to roll back after that successful return. The observer then counts zero claims and zero new validation-evidence rows or links for the attempt. |
| Commit after return | Repeat the successful call on a fresh ID. After the enclosing commit, the observer counts exactly one new assertion for the attempt. Its ID equals both the proposed and returned ID. Verify the stored `PENDING_REVIEW` state, subject, Party, time, content and evidence against the admitted intent. Recompute the complete canonical assertion digest. Fetch the trace and domain payload by the returned bindings, recompute both digests and check that they bind the same assertion, intent and authority evidence. Verify same-batch reachability and zero review decisions or accepted consequences. |
| Caught failure after staging | Let the real writer stage its rows and then raise a Python exception before returning, while PostgreSQL still reports an active transaction. Catch it **inside** the outer block and exit normally. Require `TRANSACTION_FAILED` and confirm that the observer counts zero assertions and zero new validation evidence. A test-only fault at the return boundary must preserve real inserts and the real transaction manager. |
| Domain refusal | Alter a bound input such as the asserting Party, or supply evidence from a different attempt. Require refusal with zero new claims and zero successful validation evidence. Reject a conflicting pre-existing assertion ID while preserving its original bytes. |
| Missing promotion trace | After real staging, omit the Commit Ingress trace or its link and attempt commit with constraints enforced. Require database refusal for the selected record kind and an independent count of zero new assertions, validation records and links. Verify the existing positive path with exactly one matching trace and edge. |
| Writer finalization and second connection | Observe the writing backend and full transaction ID from batch allocation through staging. Verify that a second connection cannot see any of the rows before the outer commit and that rollback removes them. Check the production dependency and callable surfaces for connection acquisition, transaction control or arbitrary SQL. |
| Unverified verdict or wrong ID | Present a caller-supplied `PASS`, a well-formed trace over different source bytes, a verifier for a different contract ID or result schema, or a new unused result ID different from the authorized effect subject. Each must refuse before a successful handoff and persist zero claims and zero successful evidence. |
| Wrong transaction or attempt | Try a foreign tenant, batch or prior attempt, and a replay of a completed operation. The guard refuses mismatched inputs. A replay stays on #178's saved-result path. Count zero additional writer dispatches and zero new rows. |

The later integration under #178 must also show the writer waiting behind #392's protected read, successful completion after release and exact retry returning the saved original result and ID with one pending claim and one successful consumption. That is a separate check from the writer acceptance cases. [Integration owner](https://github.com/samovers/OFARM2/issues/178)
