## What a successful return means

A new, admitted `ASSERT_OPERATION_CLAIM` attempt can stage exactly one immutable `OPERATION_CLAIM_ASSERTION` with `claimState = PENDING_REVIEW`. The protected assets are the assertion, its validation evidence and the existing records it refers to. The writer returns while the caller still owns the transaction. At that point the caller can read the staged bytes and can still roll back the entire write.

1. **#178 identifies a new eligible attempt.** It checks the saved operation under its concurrency guard, binds the original intent and supplies the selected authorization, assertion-act evidence, applicable gate evidence and protected inputs. The selected rule and guards must cover this action, tenant, attempt, result ID and exact proposed bytes. A completed operation goes directly to #178's saved-result path. ## Which interfaces must exist

**Transaction access.** The live tenant object exposes batch allocation and a resolver dedicated to `COMMIT_OPERATION_CLAIM_DRAFT`. That resolver must precede `begin_batch` and its command expressly forbids emitting an assertion. For the assertion command, the required order is selection of the applicable binding, batch allocation and then the guarded write. #178's transaction owner needs to provide the typed call, preserve its rollback-only and closed states, and review the corresponding public-method, constructor and slot checks. A line-budget change needs its own justification if the implementation requires one. Pass the writer access only to its claim operation. [Current transaction](../../kernel/tenant_uow.py) · [Architecture checks](../../conformance/rewrite_architecture_check.py) · [Draft batch membership](OFARM_Operation_Claim_Draft_Temporal_Command_RFC_v0_1.md#durable-batch)

**Domain authority.** The caller can supply claim content. Trusted producers must supply the selected package, authority path, assertion act and protected state for the attempt. An offline comparison can match fields even when it lacks proof of the asserting Party. The extracted v0.1 assertion permits `PENDING_REVIEW`, but it cannot express the complete typed content and evidence required here. The domain owner must identify the reviewed, selected protected-effect, result, body and evidence contracts and their permitted use. Isolated construction requires the exact candidate-consumption decision in the domain contract. Production use requires its promoted, verified extraction. The writer trusts the database, approved producers and process integrity. A compromised database administrator or application process is outside its model. [Extracted result schema](../../contracts/kernel/OFARM_AssertionRecord_schema_v0_1.json) · [Domain construction and promotion](https://github.com/samovers/OFARM/blob/6c5c6eb754baecfa38b7e364fc3d0318ae1ad89f/package_meta/history/clean_baseline_migration/phase_reports/assertion_record_submission_protected_effect_contract_rfc_candidate_v0_1.md#L824) · [Complete typed-claim verifier](https://github.com/samovers/OFARM/pull/47)

**Storage.** The existing ledger binds each record to a tenant, batch, full transaction ID and runtime bundle. Kernel reachability also requires an authoritative assertion to appear in exactly one same-transaction promotion trace. The v0.1 database constraint checks the matching `PROMOTION_EMITS` edge at commit. This trace serves a different purpose from the protected-effect validation trace. Before construction, identify the owner supplying the former and the selected storage references for the latter and its domain payload. Preserve both checks through commit. A new record-kind string must never serve as a way around the existing reachability rule. [Kernel reachability](../../KERNEL.md#the-reachability-invariant) · [Database constraint](../../kernel/migrations/0001_initial.sql)

The proposed change in #422 covers the domain writer and its PostgreSQL tests. A separately reviewable #178 prerequisite should deliver the guarded invocation and its conformance checks. Only that narrow interface precedes the writer. The complete #178 saved-result and retry integration follows it. Changes to selection authority, database privileges, canonical contracts, retention, or public routes remain with their owners. A different authority assignment or evidence representation requires a revised design before implementation.

## PostgreSQL acceptance

Use the production writer under the tenant role, with real selected inputs and the same backend throughout the call. Start each case with a distinct admitted claim ID and attempt. Use a fresh, authorized observer transaction after each outcome and show that it can read a known committed record and its evidence for the same tenant. For the commit case, the caller stages any companion records required by the active transaction contract through their owning operations. Count all new assertion and evidence rows for the attempt and follow the returned references as well. Counting just the expected ID could miss a duplicate with a different ID. Pre-existing source evidence must survive each case.

| Case | Observation required |
| --- | --- |
| Rollback after return | In the writing transaction, resolve the returned ID, validation trace and domain payload. A separate connection sees none of these new rows. Force the caller to roll back after that successful return. The observer then counts zero claims and zero new validation-evidence rows or links for the attempt. |
| Commit after return | Repeat the successful call on a fresh ID. After the enclosing commit, the observer counts exactly one new assertion for the attempt. Its ID equals both the proposed and returned ID. Verify the stored `PENDING_REVIEW` state, subject, Party, time, content and evidence against the admitted intent. Recompute the complete canonical assertion digest. Fetch the trace and domain payload by the returned bindings, recompute both digests and check that they bind the same assertion, intent and authority evidence. Verify same-batch reachability and zero review decisions or accepted consequences. |
| Caught failure after staging | Let the real writer stage its rows and then raise a Python exception before returning, while PostgreSQL still reports an active transaction. Catch it **inside** the outer block and exit normally. Require `TRANSACTION_FAILED` and confirm that the observer counts zero assertions and zero new validation evidence. A test-only fault at the return boundary must preserve real inserts and the real transaction manager. |
| Domain refusal | Alter a bound input such as the asserting Party, or supply evidence from a different attempt. Require refusal with zero new claims and zero successful validation evidence. Reject a conflicting pre-existing assertion ID while preserving its original bytes. |

The later integration under #178 must also show the writer waiting behind #392's protected read, successful completion after release and exact retry returning the saved original result and ID with one pending claim and one successful consumption. That is a separate check from these four writer cases. [Integration owner](https://github.com/samovers/OFARM2/issues/178)
