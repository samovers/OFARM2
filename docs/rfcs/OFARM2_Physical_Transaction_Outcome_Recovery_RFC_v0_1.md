# Physical transaction outcome recovery — Phase A candidate v4

Delivery [#404](https://github.com/samovers/OFARM2/issues/404), draft [#405](https://github.com/samovers/OFARM2/pull/405). This is a design for one immediate, bounded observation after ambiguous COMMIT, delivered to the caller of `ApplicationRuntime.tenant_unit_of_work(principal)`. It is not implementation acceptance or approval.

Primary trust boundary: **physical transaction outcome integrity**. The PR owns the private observer, manager integration, necessary pool-check transport bounds, focused PostgreSQL tests, architecture checks and documentation. Existing principal, tenant, binder, key, audit, migration and continuity authorities stay with their owners. The current candidate changes this RFC only; the eventual implementation remains subject to the Delivery Protocol's reviewed decision and approval.

## Problem and smallest useful capability

At base `bccb7a1f0cd5d4c81d21898e4b0978830904b716`, the tenant manager discards the original connection and raises `TenantBoundaryError(FINALIZATION_UNKNOWN)` if COMMIT raises or final state is not idle. A real committed transaction can therefore be indistinguishable to its caller from an abort or still-running transaction. The existing `GovernedWriteBatch` already supplies the database-stamped top-level xid8 and exact batch metadata.

Candidate v4 retains this call's actual validated batch and a read-only observation of the original transaction's recovery eligibility, then obtains one fresh observer checkout only after ambiguous finalization has released the original lease. Recovery is conditional on proposed support choice **P1** below: effective synchronous commit on the original transaction and reliable recovery of the same primary/WAL history. There is no reserved session during ordinary work, pre-yield xid query, detached-context registry, later-observation API, caller-held recovery handle or second durable journal. Missing validated batch or ineligible/unknown posture yields UNKNOWN. In particular, no returned batch does **not** mean no batch committed.

The delivery path is:

`ApplicationRuntime.tenant_unit_of_work` → `SecurityAuditRuntime` → `RequestRouterAuditProducer` → `TenantUnitOfWorkManager` → existing ambiguous-finalization branch → one observation → raised boundary error at the runtime caller.

The concrete output channel is a private read-only `physical_observation` property on the raised `TenantBoundaryError(FINALIZATION_UNKNOWN)`, containing one frozen value. Ordinary entry errors have no observation. The original outcome, safe error string and exception qualification remain unchanged. The router propagates this same error on exit. Acceptance inspects the exception caught **outside `runtime.tenant_unit_of_work(...)`**, not a manager attribute. The current runtime boundary has no governed HTTP handler; this makes the fact available to its present internal caller, without claiming a deployed endpoint or automatic consumer action.

These remain **historical physical facts**: COMMITTED means the original top-level transaction committed; ABORTED means it ended by abort or crash recovery without committing, not that a separate ABORT record necessarily survived. Neither grants a logical operation result, NO_EFFECT or retry permission, nor guarantees survival of a future storage/history failure. A fully received, qualified conclusion survives later cleanup loss. Unlike v3, naked committed status is insufficient: committed plus absent becomes UNKNOWN, including the test-only before-batch savepoint case. Effective-off sessions lose optional recovery even if their outcome could have been observed before a crash. Those are explicit proposed capability restrictions, not already accepted behavior. P1 and S1 remain unaccepted; the previous implementation decision remains on hold. No original durability setting is enforced.

## Effects, limits and authority

Permitted effects are read-only eligibility metadata in the existing batch INSERT response; call-local capture of the existing validated batch object; one optional fresh pool checkout after ambiguity; fresh binding and fixed read-only status/batch queries; a frozen private error attachment; and cleanup. A bounded replacement for the existing checkout health probe checks the same connection-health condition without allowing a stalled network to defeat the checkout bound. It changes no SQL authority or tenant verdict. The observer rolls back its own binder transaction; it commits no observation record.

Non-effects: no extra business write, migration, role or grant; no logical operation key, attempt, NO_EFFECT, retry permission, ALLOW, semantic-success result, decision consumption, protected payload disclosure, source-policy adoption, audit event, endpoint activation or deployment. No second COMMIT or automatic retry. Original business-query, binder and role deadlines are unchanged. Only the pool health probe and new observation reads receive explicit transport limits.

The protected asset is correct association of a physical fact with the **original** transaction. Trusted inputs are the surviving manager call, original binding, original transaction's physical connection and validated database-returned batch/eligibility observation, under P1. Request IDs, authored batch IDs, caller xids, reconstructed tuples, copied errors and claimed status are untrusted. The application facade exposes neither SQL nor a connection. Arbitrary process mutation, database-owner compromise and server/storage corruption remain excluded compromise; ordinary same-history server crash, pool pressure, cancellation, stale caller input and reply loss are in scope. This is not generic failover or replica recovery.

| Owned fact/action | Authority and invariant |
| --- | --- |
| Principal, tenant, Party and registration | Existing principal and binder owners. Fresh binding must accept the same authenticated principal and match the original protected identity fields; no copied capability is replayed |
| Original xid and batch tuple | Existing batch INSERT trigger and allocator, on the original uninterrupted connection. Retain the actual validated `GovernedWriteBatch`, including `created_at`; do not mint a second identity |
| Recovery eligibility | Original INSERT's read-only setting observation plus P1's effective-setting stability and same-history premises. A guard is not deployment admission or a durability-setting writer |
| Whole-transaction status | PostgreSQL `pg_xact_status(batch.full_xid)`, interpreted with P1 and the complete association rule below; numeric status alone cannot prove COMMITTED |
| Batch occurrence | A separate bound query by `(tenant_id, full_xid)`, compared with every field of the retained tuple. Existing stamping, unique constraint, RLS and immutability remain authoritative |
| Finalization | Existing tenant manager. Close the unit before finalization; discard original connection on ambiguity; no re-entry |
| Result delivery | One immutable observation on the existing error, reaching the runtime caller after cleanup |
| Logical outcome, retry and disclosure | Respective downstream owners, never this observer |

## P1 — proposed effective-setting and same-history support contract

The original transaction must use **effective `synchronous_commit=on` through COMMIT**, with `fsync=on`, PostgreSQL's required crash-safe storage configuration and storage that honors flushes. The observer must reach the **same accepted primary and authoritative WAL history**, including ordinary crash recovery/restart of that history. An arbitrary replica, divergent promotion, transparent failover to a different history, clone, rewind or restore does not qualify. No new deployment, readiness or continuity admission is added; #193 and existing owners retain their decisions. This RFC does not claim that current production composition attests these premises. Their real-role acceptance fixture must record them, and deployment admission remains separate work.

Capture the original setting where the batch is allocated, not in a pool configure callback or on the later observer. Append one read-only boolean expression to the existing INSERT RETURNING list: `pg_catalog.current_setting('synchronous_commit') = 'on' AND pg_catalog.current_setting('fsync') = 'on'`. Retain it privately alongside the actual validated nine-field batch; the public batch type and its nine-field authority validation stay unchanged. Adapt the private allocator/manager return plumbing without adding another SQL round trip, batch rejection or new write. A false, missing or malformed eligibility value disables recovery, while a valid batch continues through ordinary work. Existing batch-validation failures keep their current propagation. No SET, flush polling or durability enforcement is permitted.

That read proves the allocating backend's posture **at capture**, not future stability. In the proposed supported composition, the provisioned `ofarm_app`/`ofarm_worker` fixed role default, or fixed higher-priority startup setting, supplies on; the one original backend remains bound from BEGIN through COMMIT; trusted facade SQL/callbacks never SET a different value; and the configuration/storage owners preserve the premises until finalization. The role setting has precedence over a changed configuration-file default; a DSN `options` override can nevertheless select off and is caught at actual allocation. The guard does not prove any future administrative change harmless. If that stability cannot be established, this recovery contract is unsupported; do not silently claim the point-in-time guard establishes it.

Source limits matter: `deployment/postgresql/provisioning_specs.py` sets role defaults; `kernel/runtime_config.py` only checks DSN syntax and the tenant pool forwards those options. `schema_posture.configure_session` belongs to the legacy Store path, not this production manager. DISCARD ALL/RESET ALL is not a universal reset to the connect-time value. A successful callback, client object, socket, PID or observer's own on setting cannot attest the original transaction. A pooler is not approved by this RFC: its selected original backend must preserve the whole transaction and its setting, and later observation must preserve the accepted history. Idle backend substitution is no longer a reserved-window dependency, but substitution within the original transaction remains unsupported. No PID continuity detector or generic proxy/failover support is claimed.

P1 restricts **optional recovery**, not the settings accepted for ordinary work: off/unknown capture still permits the unchanged batch and COMMIT path, but ambiguity yields UNKNOWN. Only exact on is selected in this candidate; broader locally durable modes need an explicit support revision. `fsync=off`, unsafe page-write configuration, lying storage and history loss are outside the durability premise even when synchronous_commit says on. A setting read does not certify hardware. Recovery after application loss still needs a separate capability because the trusted tuple is call-local.

## Exact association and crash argument

The manager captures only the batch actually returned by its existing validated allocator and the adjacent eligibility value, after original BEGIN/binding. Its UNLOGGED binder context is not a durable xid fence. The facade supplies no raw SQL or savepoint API; caller-authored IDs and reconstructed tuples never enter the observer. No connection is acquired until ambiguity has discarded and returned the original lease. The observer obtains fresh authority and compares all nine fields, including the server-returned knowledge_position and created_at, with that retained object.

This is a conditional association argument, not a claim that created_at is a nonce or that xid8 is globally permanent. Permitted writers remain subject to the existing stamped full_xid, transaction-key uniqueness, immutable batch and tenant binding/RLS. Another supported caller cannot read an uncommitted original tuple or supply its server-returned fields through the facade. A different transaction after real xid reuse can have the same numeric xid or authored IDs, but its differing complete row must never yield COMMITTED. No newly assumed all-knowing tuple forger justifies retaining the removed reservation. An actor with the genuine tuple after an original visible commit has not disproved historical COMMITTED.

Under P1, an original commit of this logged batch flushes its commit record before becoming an externally observable committed transaction. Ordinary recovery of that history preserves it and advances xid allocation past it. Therefore (a) full matching visible batch evidence can establish original COMMITTED; (b) fresh committed status without that match cannot distinguish a reused xid and is UNKNOWN; and (c) fresh aborted status cannot conceal a prior original historical commit, so it establishes original abort/crash termination even if the number was reused and that replacement aborted. Without P1, (c) fails when a visible asynchronous commit is lost, including with an unreused xid. NULL, in-progress, future-xid SQLSTATE 22023 and incomplete/error replies supply no abort proof. PostgreSQL's [commit ordering](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xact.c#L1391-L1422), [recovery xid advancement](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xlogrecovery.c), and [status implementation](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/utils/adt/xid8funcs.c#L600-L640) support this inference; real crash controls below remain required.

Neither fresh binding nor `pg_postmaster_start_time()` authenticates the original xid/history. A child crash can recover under the same postmaster. The known numeric-reuse hazard remains documented in the [PostgreSQL developer discussion](https://www.postgresql.org/message-id/Y9SKuootyLVoJDid@paquier.xyz); removing the reservation does not remove that hazard or relax a continuity refusal.

## One finalization and observation path

State is call-local: `NO_CAPTURE → CAPTURED → CLOSED → OBSERVING → DELIVERED/CLEANED`. Missing/failed validation or ineligible capture leaves recovery unavailable. Ordinary rollback or success needs no observer; only ambiguity attempts a new lease. There is no retain/reobserve transition. No recovery refusal prevents the existing batch allocation or ordinary COMMIT. Existing allocator exceptions keep their propagation and transaction semantics.

On a body exception, rollback-only path or ordinary COMMIT success/idle verification, use existing original cleanup and release call-local capture. No status query is needed. On ambiguous finalization:

1. Close the exposed unit, preserve the original failure, discard and return the original lease exactly once **before** checkout. If no eligible captured batch exists, attach UNKNOWN with batch UNAVAILABLE and a bounded recovery-unavailable reason. Otherwise make the single bounded checkout attempt below from the same pool. Exhaustion/failure yields UNKNOWN without replacing the original error.
2. On the fresh healthy idle connection, start a READ COMMITTED transaction and obtain a fresh TenantBinding through the existing binder/minter. Retain original binding identity for comparison. The fresh nonce and key lifecycle may differ as allowed by their owners; the principal equality, immutable principal binding, tenant registration and Party identity must remain exact. Revocation or incompatible lifecycle evidence refuses through the existing owner. Never reuse the original capability. Binding failure yields UNKNOWN and preserves its actual existing refusal class separately from the original finalization failure.
3. Read `pg_xact_status(original_batch.full_xid)` with a fixed parameterized statement. The parameter comes only from the actual returned batch owned by this call. No caller input or lookup API exists. NULL, in-progress, SQLSTATE 22023 (xid in the future), any query error and incomplete reply are not abort proof. Do not reconnect or retry the failed observation transaction.
4. If possible, use a **separate subsequent READ COMMITTED statement** to read the existing batch by original tenant and full xid. Compare tenant_id, batch_id, full_xid, authenticated_principal_ref, governed_operation, request_id, runtime_bundle_digest, knowledge_position and created_at with the retained object. No protected result payload is read. There is at most one row by the existing transaction-key constraint. This order avoids using a pre-commit snapshot to claim absence after terminal status.
5. Combine fully received observations below, roll back the observer, prove idle or discard, and return its lease exactly once. Attach the frozen observation to the original error and raise it to the runtime caller. Observer/cleanup failure cannot replace the original error or erase an already qualified conclusion; contradictory complete evidence is handled by the table. No recursive recovery of the observer's own rollback is attempted.

The frozen observation contains `physical_status` (COMMITTED, ABORTED, UNKNOWN), separate `batch_observation` (MATCHING_COMMITTED, ABSENT_AT_OBSERVATION, CONFLICT, UNAVAILABLE), received evidence/basis, any `integrity_problem`, bounded `observer_failure`, and cleanup disposition. No connection, callable, raw credential, capability, SQL error text or recovery handle crosses in this value. The evidence identifies original xid distinctly from the observer's xid. These are private physical terms, not new canonical RuntimeProblem or transaction-outcome values.

| Received status under P1 after valid capture/binding | Separate batch observation | Physical conclusion |
| --- | --- | --- |
| committed | complete matching row | COMMITTED |
| committed | absent, unavailable or partial | UNKNOWN; raw committed status is not associated original commit proof |
| aborted | absent | ABORTED; no logical NO_EFFECT or retry consequence |
| aborted | later batch read unavailable/partial | Retain qualified ABORTED under P1; batch UNAVAILABLE |
| in progress or NULL | complete matching original committed row | COMMITTED from the exact row; earlier status may have raced completion |
| in progress or NULL | absent/unavailable | UNKNOWN |
| aborted | matching row | Preserve raw contradiction; UNKNOWN plus integrity_problem, no usable success or negative conclusion |
| any | returned row differs from the retained tuple | UNKNOWN plus CONFLICT; retain raw evidence, forbid original-commit or batch-success use |
| missing/ineligible capture, binding refused, 22023, other error or incomplete status | no usable evidence from this path | UNKNOWN and batch UNAVAILABLE; never reconstruct or retry |

If a qualified conclusion was fully received before cleanup loss, retain it with honest cleanup failure. Receiving only committed status does not qualify; COMMITTED requires the matching row. ABORTED may qualify before the batch read under P1, but a later contradictory/differing row downgrades it as specified above. Partial replies are not facts. No second post-loss checkout or later lookup is permitted. The error observation grants no ability to query again.

Whole-transaction status and batch occurrence stay distinct. A test-only savepoint before allocation can remove the returned row while the outer transaction commits: this candidate returns UNKNOWN plus ABSENT_AT_OBSERVATION and retains raw committed status. That loses v3's COMMITTED-plus-absent recovery and must be visible in the next decision, despite there being no public savepoint API. A savepoint after allocation may retain the batch while rolling back later writes: matching batch proves no command/domain success. Still-running queued work is UNKNOWN; closing a socket, missing rows, timeouts or acquiring a lock never prove abort. No tenant write/advisory lock is acquired to manufacture a negative proof. See [READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED) and [savepoint lock behavior](https://www.postgresql.org/docs/17/explicit-locking.html).

## Resource, timeout and cleanup contract

All original and observer leases share the existing maximum **8** connections and **32** waiting requests. There is no extra pool, bypass connection, registry or detached reservation. Each call holds at most one tenant lease at a time: the original is discarded/returned before the observer is requested. Eight ordinary bodies no longer compete for a second reservation, and the four-paired-call limit is removed. A released slot is not reserved for its former caller; pool pressure can still make recovery UNKNOWN.

The fresh observation uses one `getconn(timeout=0.1)` attempt: a 100 ms queue budget, without increasing pool/waiter limits or looping in application code. Zero is not used because pinned psycopg-pool 3.3.1 rejects expired timeouts even when a connection is ready. A late assignment belongs to the pool's failed-checkout cleanup; it is not a usable observer. Exhaustion leaves recovery unavailable, not a retry or service-wide refusal.

The queue timeout alone does not bound the pool's network health callback. Replace only the existing empty-query checkout probe with an equivalent fixed probe using an absolute monotonic **2-second** transport deadline. Reuse pinned psycopg's protocol machinery and S1's proposed bounded wait adapter; do not duplicate send/flush/result parsing or abandon a background query/thread. Expiration closes/discards the connection in its owning operation, without a blocking cancellation handshake. This companion affects shared checkouts while preserving the same healthy/idle condition and original isolation/reset rules. It adds no tenant SQL, role, lifecycle or readiness decision. One checkout allows 100 ms queue/backoff plus one in-progress 2-second probe and normal scheduling overhead; prove pool failed-check retries cannot renew the allowance indefinitely. These are phase bounds, not a universal physical-outcome deadline.

No observer exists while original work runs. There is no retention timer or promise after application loss. Once the fresh observation starts, loss or shutdown ends that one attempt; do not reconnect/reset it to continue. The original call owns its lifetime and cleanup. Every acquired lease reaches exactly one pool return/discard, including body errors, allocator failures, observer cancellation and shutdown. Retained errors contain no resource or live context.

On the new observer transaction, use local statement_timeout 2,000 ms and lock_timeout 500 ms. Every added database exchange, including fresh-binding SQL and rollback, also has a 2-second client transport deadline with close/discard on expiry. Reuse the existing binder sequence and validation with bounded waiting. The finite successful path has nine fixed exchanges: BEGIN; one local-timeout setup statement; create challenge; read challenge; bind capability; read context; status; batch; rollback. No polling SQL loop or recursive recovery exists. Cancellation interrupts supported waits; no original-backend cancellation is issued. Network-level tests must demonstrate each bound and resource disposal.

**Separate prerequisite S1: [Delivery #406](https://github.com/samovers/OFARM2/issues/406), draft [#407](https://github.com/samovers/OFARM2/pull/407).** The authority reader's separate blocking connection/query/receipt/cleanup path can stall minting during ordinary entry, startup and observer binding; an observer socket deadline cannot interrupt it. S1 must supply finite cancellable observation with unchanged credentials/validation. Its revised driver-wait design, support choice H1 and runtime evidence remain unaccepted; references here are a proposed mechanical interface, not acceptance. Reconcile that interface before implementation; PR405 adds no second reader, protocol loop, abandoned worker, signing-policy or principal decision. S1 owns its shared-DSN/whole-startup compatibility disclosure. Its provider connections remain outside the tenant pool's eight leases.

**Actual PR405 cancellation integration (PR407 FU-2):** at the source base, `CapabilityMinter.mint` in `kernel/tenant_uow.py:36–43` has only three arguments and `_bind` calls it at `:436–438` without cancellation. PR405 owns extending that local Protocol with optional keyword-only `cancel_event: Event | None = None` and `deadline_monotonic: float | None = None`, and adding the same internal keywords to `_bind`. Before observer `_bind`, its owner passes the call-local event and an absolute `time.monotonic() + 5.0` provider deadline. The two preceding challenge queries consume that caller budget; do not renew it at mint. `_bind` forwards **both unchanged keywords at the real `self._minter.mint(principal.identity, principal.authority, challenge, ...)` call**. S1 owns issuer forwarding into `SigningAuthorityReader.current`, its minimum of owner/caller deadlines, and the pre-KMS cancellation/expiry check. Ordinary binding omits these optional values and retains S1's mandatory owner bound. Do not add a new runtime/facade cancellation API or a second Protocol/validator.

The private observation scope owns its event and marks it on cancellation/abnormal exit before cleanup; all its bounded SQL waits see the same signal. PS11 must exercise the actual event during the real minter call through a fault seam, not replace minting with a successful fake. This proves the composed path's interruptibility, not a newly deployed public cancellation channel. The provider deadline bounds authority observation, not an already-dispatched KMS RPC. The existing signer uses retry=None and a configured finite RPC timeout (5 seconds by default, constructor ceiling 30); cancellation after dispatch cannot undo it. After mint returns, recheck cancellation before binding/querying and clean up. Total latency includes checkout, at most nine SQL phase bounds, S1's at-most-5-second provider phase under H1, existing finite KMS behavior and supported local work/scheduling. Do not advertise a two-second or 50-ms whole-call guarantee or change KMS custody/deadlines here.

Original entry failures retain current pre-tenant audit routing. Observation happens after original binding. Do not broaden `RequestRouterAuditProducer`'s entry-only catch to cover body, finalization or observer binding, and do not add FINALIZATION_UNKNOWN to its audit reasons. No new audit event/channel is introduced.

## Simpler alternatives and independent follow-ups

N2 selects the credible simpler rule with its explicit P1 restriction: fresh checkout, complete nine-field match for COMMITTED, qualified aborted for ABORTED, otherwise UNKNOWN. N1 stays closed. The removed reserved-session design's concrete extra benefit was historical ABORTED for effective-off sessions without confusing their lost commits with aborts, plus committed-without-batch recovery. Its cost was a second lease during work, paired capacity, reservation ordering, uninterrupted observer-backend assumptions and loss of ordinary synchronous crash recovery. No deployed effective-off recovery consumer has been established. Those costs are not justified merely to preserve an unapproved candidate. P1 changes the proposed support contract without enforcing original settings; it must be accepted in a replacement decision before coding.

The concrete negative case needs no malicious actor or secret tuple knowledge:

1. The real manager receives its validated batch on an original session with effective `synchronous_commit=off`, then sends COMMIT whose reply is lost/withheld.
2. PostgreSQL marks that original transaction committed. An already bound ordinary-role reader sees its genuine row before the COMMIT WAL is durable. This reader witnesses visibility; it does not forge a replacement.
3. Crash recovery loses the unflushed commit. A fresh status can report `aborted` for the original numeric xid: either the same unreused number whose INSERT WAL survived, or a genuinely reused number whose replacement aborted.
4. An unrestricted fresh rule labels the original ABORTED from recovered state, despite its witnessed historical commit. Under this candidate the actual off capture disables recovery before those facts are interpreted; the runtime caller receives UNKNOWN. A setting checked on another backend would not justify that refusal behavior.

This schedule is **source-supported, not an executed crash result in this RFC pass**. The new review reports stand-in PostgreSQL experiments, not this repository's actual-role acceptance. PostgreSQL documents completion before durability and loss after crash for [asynchronous commit](https://www.postgresql.org/docs/17/wal-async-commit.html); [WAL settings](https://www.postgresql.org/docs/17/runtime-config-wal.html) make effective commit-time posture and reliable fsync relevant. Existing role defaults do not enforce the session value. PS18 tests the guard's refusal of unsupported off recovery and the real asynchronous counterexample, not successful recovery of off transactions.

A copied full tuple after an original asynchronous commit would not demonstrate false **historical COMMITTED**: the original did commit. Nor is a supported separate SQL actor's knowledge of the lost, uncommitted original tuple established here. Those are not reasons to reject the selected simpler path. The existing complete tuple comparison and hostile-role controls remain necessary.

Enforcing synchronous commit would change original behavior and is not selected. A positive-match-only design would avoid the negative inference but give up useful ABORTED entirely. Retaining the window to support off settings would require an identified need justifying its cost. The selected P1 proposal preserves both useful outcomes within its narrower contract, including ordinary same-history crash recovery, while explicitly losing committed-plus-absent savepoint recovery.

Making the batch INSERT WAL durable before ambiguity can prevent numeric xid reuse because [WAL record construction](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xloginsert.c) carries the xid and [replay](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xlogrecovery.c) advances nextXid. It still does not prove the later asynchronous COMMIT durable: INSERT WAL can survive while that commit is lost, leaving fresh `aborted` for the same unreused xid after a historical visible commit. A high post-reconnect flush LSN repairs neither fact. A commit-durability proof is a different capability; this candidate adds no flush polling, WAL write or second fallback. PS18's unreused-xid variant keeps this distinction falsifiable.

Two reviewer-reported base defects remain separate work at the original allocator/finalization owner:

- **F1:** a swallowed SQL error may leave INERROR; psycopg COMMIT can finish as rollback without raising, and today's manager may return normally. This design observes ambiguous finalization, not every ordinary return, and must not claim to repair that case.
- **F2:** allocation validation can raise after INSERT without marking rollback-only; a caller that swallows it may commit a row despite having no returned batch. This design adds no new allocator rejection and treats missing validated return as UNAVAILABLE, never NOT_ALLOCATED or ABSENT. There is no observer lease to release on that exception.

The complete separate correction is effective rollback-only propagation for failed batch allocation and honest ordinary-finalization failure behavior, with swallowed-error controls. It is a prerequisite before a downstream command consumer can rely on ordinary return or allocator rejection as proof of committed/absent effects. It is not required to infer this observer's finite facts: F1's described path never enters ambiguous recovery; F2 supplies no usable returned batch; neither absence nor ordinary return is a recovery proof. No source owner or failure semantics are silently amended. #178's logical operation fence and #193's continuity admission remain independent prerequisites for their own capabilities under #167.

**Conditional review dispositions:** N2 is addressed by this proposed smaller design, subject to focused review and P1 acceptance. PR405 FU-2's special direct-primary/idle-session-continuity composition prerequisite falls away with the reservation; no nonexistent production composition owner/test is claimed. Actual deployment support for the same-history/durability premises remains with separate deployment/continuity work, not a new PR405 gate or silent admission change. P-3's PID-change detector no longer serves an observation-window invariant and is not added; PID equality never proves topology. P-4 is included as explicit 22023 UNKNOWN and separate INSERT/COMMIT LSN evidence. PR407 FU-2's local Protocol/call-site changes are paid for below. Earlier error delivery, missing-return, audit and N1 corrections are retained.

## Implementation shape and explicit architecture budget

Expected areas are `kernel/tenant_uow.py`, one private `kernel/tenant_physical_outcome.py`, focused runtime/manager/PostgreSQL tests, the architecture checker and Kernel documentation. Reuse the existing batch type, nine-field validation and binder. Adapt the private allocator return to carry the adjacent eligibility bit to its manager wrapper, which still returns only GovernedWriteBatch to the unchanged slotted facade. Reuse S1's proposed mechanical driver over a Wait-yielding psycopg generator, current-socket getter, absolute monotonic deadline and event. That driver owns only waiting/generator cleanup; PR405 owns the connection/lease and fixed health/binder/query operations. Do not import signing policy or duplicate protocol/authority validation. The minter Protocol and actual `_bind` forwarding belong in tenant_uow.py. No production consumer may inspect facade mangled state. Delivery remains the error channel, not a new application-runtime API.

Base source measures **520 lines** in tenant_uow.py and **412** in the selector: **932/940** for the tenant-transaction group. This smaller candidate proposes a tenant_uow.py ceiling of **600**, a private-module ceiling of **260** (down from 320), and group ceiling **1,280** (600 + existing selector ceiling 420 + 260, down from 1,340). The current zero-headroom limit is not sufficient. These are proposed upper limits, not measured implementation or changed gates. Preserve the 80-line function limit and facade/import/isolation checks.

The 80-line integration allowance is explicitly allocated: imports/error attachment 14; INSERT eligibility/private capture plumbing 18; original lease return-before-observe and delivery 20; **CapabilityMinter Protocol, `_bind` keywords and actual mint forwarding 20**; bounded pool-probe wiring 8. The private module's 260-line allowance covers immutable observation/combiner 80, bounded fixed-query/binder adapter and fresh-checkout ownership 100, and cancellation/deadline/cleanup 80. S1's one shared driver-wait implementation is charged in its own group; PR405's imports and adapter use are charged here. This is a source-based planning allocation, **not measured working implementation**. Implementation must measure the whole vertical path, including mechanical test doubles/protocol typing, with no unbudgeted helper, compressed formatting or facade exemption. If complete clear code does not fit, return the measured reason for a revised budget/design rather than evading the checker.

Implementation rollback removes observation and restores the original unresolved error behavior without deleting batches or reinterpreting already delivered facts. No migration rollback is needed. A required new grant, role, durable identity registration, independent continuity authority or changed binder/audit decision stops this scope and becomes a separate prerequisite; it is not an opportunistic correction here.
