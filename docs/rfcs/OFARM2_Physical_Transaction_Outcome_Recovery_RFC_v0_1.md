# Physical transaction outcome recovery — Phase A candidate v2

Delivery [#404](https://github.com/samovers/OFARM2/issues/404), draft [#405](https://github.com/samovers/OFARM2/pull/405). This is a design for one immediate, bounded observation after ambiguous COMMIT, delivered to the caller of `ApplicationRuntime.tenant_unit_of_work(principal)`. It is not implementation acceptance or approval.

Primary trust boundary: **physical transaction outcome integrity**. The PR owns the private observer, manager integration, necessary pool-check transport bounds, focused PostgreSQL tests, architecture checks and documentation. Existing principal, tenant, binder, key, audit, migration and continuity authorities stay with their owners. The current candidate changes this RFC only; the eventual implementation remains subject to the Delivery Protocol's reviewed decision and approval.

## Problem and smallest useful capability

At base `bccb7a1f0cd5d4c81d21898e4b0978830904b716`, the tenant manager discards the original connection and raises `TenantBoundaryError(FINALIZATION_UNKNOWN)` if COMMIT raises or final state is not idle. A real committed transaction can therefore be indistinguishable to its caller from an abort or still-running transaction. The existing `GovernedWriteBatch` already supplies the database-stamped top-level xid8 and exact batch metadata.

Candidate v2 recovers only when that batch was successfully returned while a second, manager-owned PostgreSQL session was already reserved. The second session stays continuously leased, without reconnection, until the one immediate observation. It is both the observer and the evidence that database crash recovery has not replaced the original xid's meaning. There is no pre-yield xid query, detached-context registry, later-observation API, caller-held recovery handle or second durable journal. A call with no validated returned batch, no reserved session or lost session yields UNKNOWN on ambiguous finalization. In particular, no returned batch does **not** mean no batch committed.

The delivery path is:

`ApplicationRuntime.tenant_unit_of_work` → `SecurityAuditRuntime` → `RequestRouterAuditProducer` → `TenantUnitOfWorkManager` → existing ambiguous-finalization branch → one observation → raised boundary error at the runtime caller.

The concrete output channel is a private read-only `physical_observation` property on the raised `TenantBoundaryError(FINALIZATION_UNKNOWN)`, containing one frozen value. Ordinary entry errors have no observation. The original outcome, safe error string and exception qualification remain unchanged. The router propagates this same error on exit. Acceptance inspects the exception caught **outside `runtime.tenant_unit_of_work(...)`**, not a manager attribute. The current runtime boundary has no governed HTTP handler; this makes the fact available to its present internal caller, without claiming a deployed endpoint or automatic consumer action.

## Effects, limits and authority

Permitted effects are one optional extra pool lease before batch INSERT; capture of the existing validated batch object; fresh binding and fixed read-only status/batch queries on that same reserved session after ambiguity; a frozen private error attachment; and cleanup. A bounded replacement for the existing checkout health probe is a necessary companion: it checks the same connection-health condition without allowing a stalled network to defeat the reservation bound. It changes no SQL authority or tenant verdict. The observer rolls back its own binder transaction; it commits no observation record.

Non-effects: no extra business write, migration, role or grant; no logical operation key, attempt, NO_EFFECT, retry permission, ALLOW, semantic-success result, decision consumption, protected payload disclosure, source-policy adoption, audit event, endpoint activation or deployment. No second COMMIT or automatic retry. Original business-query, binder and role deadlines are unchanged. Only the pool health probe and new observation reads receive explicit transport limits.

The protected asset is correct association of a physical fact with the **original** transaction. Trusted inputs are the surviving manager call, original binding, original physical connection, validated database-returned batch and its reserved session. Request IDs, authored batch IDs, caller xids, reconstructed tuples, copied errors and claimed status are untrusted. The application facade exposes neither SQL nor a connection. Arbitrary process mutation, database-owner compromise, server corruption and an undeclared clone remain excluded compromise; ordinary server crash, pool pressure, cancellation, stale caller input and reply loss are in scope.

| Owned fact/action | Authority and invariant |
| --- | --- |
| Principal, tenant, Party and registration | Existing principal and binder owners. Fresh binding must accept the same authenticated principal and match the original protected identity fields; no copied capability is replayed |
| Original xid and batch tuple | Existing batch INSERT trigger and allocator, on the original uninterrupted connection. Retain the actual validated `GovernedWriteBatch`, including `created_at`; do not mint a second identity |
| Valid observation window | Local ownership of one continuously reserved physical observer session, established before sending that INSERT. This proves only the limited session window below, not service continuity or recovery admission |
| Whole-transaction status | PostgreSQL `pg_xact_status(batch.full_xid)` inside that valid window |
| Batch occurrence | A separate bound query by `(tenant_id, full_xid)`, compared with every field of the retained tuple. Existing stamping, unique constraint, RLS and immutability remain authoritative |
| Finalization | Existing tenant manager. Close the unit before finalization; discard original connection on ambiguity; no re-entry |
| Result delivery | One immutable observation on the existing error, reaching the runtime caller after cleanup |
| Logical outcome, retry and disclosure | Respective downstream owners, never this observer |

This is provisional pre-deployment engineering. Reduced recovery availability is acceptable; a false association is not. A requirement for recovery after application loss, observer-session loss, failover, rewind or restore needs a separate design. Matching installation audience, server address, manager, pool or `pg_postmaster_start_time()` is not a substitute. No existing continuity refusal is relaxed.

## Exact identity window and crash argument

The manager wraps its existing typed batch allocator, keeping the observation state solely in the current call's local ownership:

1. Original BEGIN and TenantBinding have already succeeded. The binder may already have allocated xid X; its context is UNLOGGED and is **not** a durable xid fence.
2. Immediately before sending the batch INSERT, make one bounded reservation attempt for a **different**, healthy, idle connection from the same admitted tenant pool. It must represent one physical PostgreSQL session on the same accepted primary service, without transaction/session multiplexing, reset/reconnect or transparent failover. No runtime admission policy is added: where this existing connection model cannot be established, recovery is unavailable.
3. Keep that observer connection checked out and idle **outside a transaction**. Then run the existing INSERT on the original connection and retain the allocator's validated return. The completed INSERT response after reservation is the ordering proof: the still-original backend remained alive after the observer session existed. Do not use a previously obtained batch with a session reserved afterward. Do not reconnect the original or replay the INSERT. Failed/missing allocation validation leaves no usable recovery context, regardless of possible server-side effects.
4. Hold the reserved connection until normal finalization cleanup or the one immediate observation. Its Python connection object and underlying libpq `PGconn` remain the same; no `reset`, `reset_start`, new checkout, rebind onto a replacement session, or connection replacement may repair failure. PID equality is not evidence. The local values never leave the manager as a reusable capability.

Why this excludes xid reuse: PostgreSQL 17.10's `HandleChildCrash` ends other backends, and its state machine waits for them to exit before shared-memory reinitialization and startup recovery. A normal postmaster restart also ends these sessions. Thus a command completed on the reserved, unreconnected observer session cannot describe a post-recovery reused xid. The successful original INSERT after reservation closes the earlier race even though the binder allocated X beforehand. A crash before that response prevents capture or kills the reserved session; a crash afterward prevents post-recovery observation on it. Buffered complete pre-crash replies can remain historical observations; a buffered partial response is not a fact. This is a source-supported inference, with real crash tests required below. See [PostgreSQL 17.10 postmaster.c, HandleChildCrash and PostmasterStateMachine](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/postmaster/postmaster.c).

`pg_postmaster_start_time()` alone is expressly rejected: a child crash can trigger recovery under the same postmaster. A fresh TenantBinding authenticates its own transaction, not a historical xid. The known hazard is documented in the [PostgreSQL developer discussion](https://www.postgresql.org/message-id/Y9SKuootyLVoJDid@paquier.xyz); [xid8funcs.c](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/utils/adt/xid8funcs.c) does not turn the numeric xid into durable external identity.

## One finalization and observation path

State is call-local: `NO_WINDOW → RESERVED → CAPTURED → CLOSED → DELIVERED/CLEANED`. Reservation or allocation failure moves to unavailable recovery; ordinary rollback, success, cancellation or observer completion releases the reservation. There is no retain/reobserve transition. A skipped reservation never prevents the existing batch allocation or ordinary COMMIT; it only removes optional recovery. Existing allocator exceptions keep their existing propagation and transaction semantics.

On a body exception or rollback-only path, finish the unit and use existing original cleanup, then return/discard the reserved connection. On ordinary COMMIT success and idle verification, return/discard it too. No status query is needed on either path. On ambiguous finalization:

1. Close the exposed unit, preserve the original failure, discard and return the original lease to its owner. Keep the reserved observer lease. If no captured batch/window exists, attach UNKNOWN with batch UNAVAILABLE and a bounded recovery-unavailable reason; do not obtain a new observer.
2. On the **same reserved session**, start a new READ COMMITTED transaction and obtain a fresh TenantBinding through the existing binder/minter. Retain original binding identity for comparison. The fresh nonce and key lifecycle may differ as allowed by their owners; the principal equality, immutable principal binding, tenant registration and Party identity must remain exact. Revocation or incompatible lifecycle evidence refuses through the existing owner. Never reuse the original capability. Binding failure yields UNKNOWN and preserves its actual existing refusal class separately from the original finalization failure.
3. Read `pg_xact_status(original_batch.full_xid)` with a fixed parameterized statement. The parameter comes only from the actual returned batch owned by this call. No caller input or lookup API exists. NULL, in-progress, query error and incomplete reply are not abort proof.
4. If possible, use a **separate subsequent READ COMMITTED statement** to read the existing batch by original tenant and full xid. Compare tenant_id, batch_id, full_xid, authenticated_principal_ref, governed_operation, request_id, runtime_bundle_digest, knowledge_position and created_at with the retained object. No protected result payload is read. There is at most one row by the existing transaction-key constraint. This order avoids using a pre-commit snapshot to claim absence after terminal status.
5. Combine fully received observations below, roll back the observer, prove idle or discard, and return its lease exactly once. Attach the frozen observation to the original error and raise it to the runtime caller. Observer/cleanup failure cannot replace the original error or erase a received terminal fact. No recursive recovery of the observer's own rollback is attempted.

The frozen observation contains `physical_status` (COMMITTED, ABORTED, UNKNOWN), separate `batch_observation` (MATCHING_COMMITTED, ABSENT_AT_OBSERVATION, CONFLICT, UNAVAILABLE), received evidence/basis, any `integrity_problem`, bounded `observer_failure`, and cleanup disposition. No connection, callable, raw credential, capability, SQL error text or recovery handle crosses in this value. The evidence identifies original xid distinctly from the observer's xid. These are private physical terms, not new canonical RuntimeProblem or transaction-outcome values.

| Received status inside the valid window | Separate batch observation | Physical conclusion |
| --- | --- | --- |
| committed | matching or absent | COMMITTED; batch presence remains separate |
| aborted | absent | ABORTED; no logical NO_EFFECT or retry consequence |
| committed or aborted | later batch read unavailable/partial | Retain terminal fact and basis; batch UNAVAILABLE |
| in progress or NULL | matching original committed row | COMMITTED from the exact row **within the proved identity window**; earlier status may have raced completion |
| in progress or NULL | absent/unavailable | UNKNOWN |
| aborted | matching row | Preserve raw contradiction; UNKNOWN plus integrity_problem, no usable success or negative conclusion |
| any | returned row differs from the retained tuple | CONFLICT; preserve any independently received status/basis, forbid batch-success use |
| no valid window, session lost, missing returned batch or binding refused | no usable evidence from this path | UNKNOWN and batch UNAVAILABLE; never reconstruct or reconnect |

If a valid terminal fact was fully received before session/cleanup loss, keep that historical fact with batch UNAVAILABLE where necessary. A new post-loss fact is forbidden, including a matching-row fallback on another connection. The error observation grants no ability to query again.

Whole-transaction status and batch occurrence must stay distinct. A savepoint before allocation may be rolled back after the tuple was returned, removing the row while the outer transaction commits: COMMITTED plus ABSENT_AT_OBSERVATION is correct. A savepoint after allocation may retain the batch while rolling back later writes: matching batch proves no command/domain success. Still-running queued work is UNKNOWN; closing a socket, missing rows, timeouts or acquiring a lock never prove abort. No tenant write/advisory lock is acquired to manufacture a negative proof. See [READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED) and [savepoint lock behavior](https://www.postgresql.org/docs/17/explicit-locking.html).

## Resource, timeout and cleanup contract

All original and observer leases share the existing maximum **8** connections and **32** waiting requests. There is no extra pool, bypass connection, registry or detached reservation after call completion. One observation-capable call consumes two leases until the original is released, then one. Consequently at most four such paired calls coexist; mixed original/observing calls still total at most eight leases. This deliberately trades concurrency for proved identity and must be visible in performance evidence.

The reservation uses one `getconn(timeout=0.1)` attempt: a 100 ms queue budget, without increasing pool/waiter limits or looping in application code. Zero is not used because pinned psycopg-pool 3.3.1 rejects expired timeouts even when a connection is ready. Eight original leases can each fail reservation within the bound and proceed with ordinary work, so none waits indefinitely for a second slot. A late pool assignment belongs to the pool's failed-checkout cleanup; it is not a usable observer. Exhaustion leaves recovery unavailable, not a rollback or service-wide refusal.

The queue timeout alone does not bound the pool's network health callback. Replace only the existing empty-query checkout probe with an equivalent fixed probe whose libpq send/receive waits use an absolute monotonic **2-second** deadline. Use nonblocking I/O and finite poll waits; expiration closes/discards that connection in its owning operation. There must be no abandoned background query/thread or blocking cancellation handshake. This shared checkout-probe companion preserves the same healthy/idle condition and original transaction isolation/reset rules. It adds no tenant SQL, role, lifecycle or readiness decision. The reservation therefore has a maximum 100 ms queue/backoff allowance plus one in-progress 2-second probe, allowing normal scheduler overhead; prove failed-check retries cannot restart that deadline indefinitely. Do not represent these as a hard physical-outcome deadline.

The observer remains outside a transaction while original work runs, so `idle_in_transaction_session_timeout` does not apply to that reservation. Any idle-session timeout, network loss, server termination, pool/manager shutdown or replacement makes its subsequent use unavailable; **never keep it alive by reconnecting**. There is no independent retention timer or promise of recovery after arbitrary delay. The original call owns its lifetime and existing cancellation. Even a stalled body cannot accumulate observer leases outside the eight-connection cap. On every exit, including successful calls and allocation exceptions, ownership must reach exactly one pool return/discard. Errors retained by callers contain no resource or live context.

On the new observer transaction, use local statement_timeout 2,000 ms and lock_timeout 500 ms. Every added database exchange on that session, including the SQL parts of fresh binding and rollback, also has a 2-second client transport deadline with close/discard on expiry; a SQL timeout alone does not cover a black-holed network. Reuse the existing binder SQL sequence and validation, adding bounded I/O without changing its acceptance rules. A cancellation interrupts/cleans the observer, and unreceived facts remain UNKNOWN. Never cancel the original backend from the observer. Network-level tests must demonstrate the bounds and that no lease, task or dirty session escapes them.

**Separate prerequisite S1: bounded capability-provider dependency.** Source inspection finds that `GoogleKmsSigner` passes an explicit five-second RPC timeout, but the production `SigningAuthorityReader` calls a separate `_connection_factory` using plain `psycopg.connect(dsn)` and synchronous query/cleanup, with no code-owned client transport bound. Receipt-file I/O is also owned by that provider. Therefore the old design's claim that the entire minting path is already bounded is not established. PR405 must not implement a second authority reader, change its credentials/allow-deny rules or hide an abandoned minting thread. Before automatic recovery can satisfy PS11, the capability-provider owner must deliver and verify a finite, cancellable observation/mint dependency through its existing interface, including connection, query, receipt and cleanup failures. Route that independently complete correction separately; do not edit that boundary in PR405. Until then, bounded end-to-end recovery is an unresolved implementation prerequisite, not an accepted result. Existing provider connections are outside the tenant pool's eight-lease count; no eight-connection claim is made for the whole application. No universal latency or signing-custody change is implied here.

The concrete S1 path is ambiguous COMMIT → release original → start reserved observer's fresh binding → `TenantCapabilityIssuer.mint` → `SigningAuthorityReader.current` → a successfully opened authority connection whose query response is then black-holed. Neither the pool deadline nor the observer-session deadline controls that separate connection. Timing out only the outer call leaves the minting work and reserved lease without completed ownership cleanup; closing the observer socket alone does not interrupt the authority query. This violates PS11's cancellation/disposal requirement even without promising a fixed successful-call latency. The smallest prerequisite is cancellation and finite transport/cleanup behavior at the existing authority-reader/provider owner, preserving its exact query, credentials and authority validation, plus a test that the caller regains control and releases resources after this failure. Propagate its unavailable result through the existing capability refusal path. Do not broaden this into a signing-policy or principal-resolution redesign. This is a source-level failure path, not an executed network experiment.

Original entry failures retain current pre-tenant audit routing. Observation happens after original binding. Do not broaden `RequestRouterAuditProducer`'s entry-only catch to cover body, finalization or observer binding, and do not add FINALIZATION_UNKNOWN to its audit reasons. No new audit event/channel is introduced.

## Simpler alternatives and independent follow-ups

The baseline alternative is one fresh checkout after ambiguity, using the returned batch and retaining nothing. That removes unused state and supplies the output channel, but cannot distinguish xid reuse after a crash; neither a matching authored ID nor fresh binding repairs it. The single reserved observer adds only the live session needed for that present invariant. It is not a general witness service or a retained registry.

An alternative is to prove the batch's WAL record durable before ambiguity. PostgreSQL's [WAL record construction](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xloginsert.c) includes a transaction ID and [replay](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xlogrecovery.c) advances nextXid past record IDs. [Insert/flush LSN functions](https://github.com/postgres/postgres/blob/REL_17_10/src/backend/access/transam/xlogfuncs.c) suggest a possible proof. A pre-crash, original-connection proof that flush passed the completed logged INSERT would need separate top-level/subtransaction and checkpoint reasoning, actual-role access evidence and useful finite flush behavior. Reading a high flush LSN only after reconnect is insufficient. This candidate does not select flush waiting/polling, new WAL writes or a second fallback: its required consumer needs no recovery across session loss. Reconsider the WAL option if measured paired-lease cost makes this narrow horizon unusable; do not combine two identity mechanisms speculatively.

Two reviewer-reported base defects remain separate work at the original allocator/finalization owner:

- **F1:** a swallowed SQL error may leave INERROR; psycopg COMMIT can finish as rollback without raising, and today's manager may return normally. This design observes ambiguous finalization, not every ordinary return, and must not claim to repair that case.
- **F2:** allocation validation can raise after INSERT without marking rollback-only; a caller that swallows it may commit a row despite having no returned batch. This design adds no new allocator rejection and treats missing validated return as UNAVAILABLE, never NOT_ALLOCATED or ABSENT. Release the unused reservation on that exception.

The complete separate correction is effective rollback-only propagation for failed batch allocation and honest ordinary-finalization failure behavior, with swallowed-error controls. It is a prerequisite before a downstream command consumer can rely on ordinary return or allocator rejection as proof of committed/absent effects. It is not required to infer this observer's finite facts, because neither defect supplies a usable captured batch on its described path and neither absence nor ordinary return is used as a recovery proof. No source owner or failure semantics are silently amended in this RFC. #178's logical operation fence and #193's continuity admission remain independent prerequisites for their own capabilities.

## Implementation shape and explicit architecture budget

Expected areas are `kernel/tenant_uow.py`, one private `kernel/tenant_physical_outcome.py`, focused runtime/manager/PostgreSQL tests, the architecture checker and Kernel documentation. Reuse the existing batch type, allocator and binder; a narrow fixed-I/O adapter may supply transport bounds to the existing binder sequence without duplicating authority validation. Keep the slotted `TenantUnitOfWork` facade unchanged. No production consumer may inspect its mangled state. Delivery is through the error channel, not a new application-runtime API.

Base source measures **520 lines** in tenant_uow.py and **412** in the selector: **932/940** for the tenant-transaction group. Therefore this Phase A explicitly proposes a tenant_uow.py ceiling of **600**, a new private-module ceiling of **320**, and a group ceiling of **1,340** including all three modules (600 + existing selector ceiling 420 + 320). The current zero-headroom limit is not claimed sufficient. These are reviewed upper limits, not targets or implemented gate changes. Preserve the 80-line function limit and all facade/import/isolation checks.

The 80-line integration allowance covers imports/error attachment (16), allocator reservation/capture hooks (16), ordinary/exception release ownership (20), ambiguous observation/delivery (20), and bounded pool-probe wiring (8). This is a source-based allocation, **not measured working implementation**. The published reviewer measured a smaller incomplete old-design hook at +14 lines; that experiment is reviewer evidence only. Implementation must measure the complete hooks and include the private module in the group—no unbudgeted helper, whitespace compression or broad facade exemption. If these finite limits cannot hold a clear complete path, return the measured reason for a revised design rather than evading the checker.

Implementation rollback removes observation and restores the original unresolved error behavior without deleting batches or reinterpreting already delivered facts. No migration rollback is needed. A required new grant, role, durable identity registration, independent continuity authority or changed binder/audit decision stops this scope and becomes a separate prerequisite; it is not an opportunistic correction here.
