# Checking that a claim ID is free

## Decision for review

**Draft PR #426 is the single implementation PR for Delivery #178.** Its full scope includes command identity, exact and changed retries, atomic save and recovery of the original outcome. This document covers one acceptance condition in that delivery. The original transaction can save its checked claim only if its proposed ID was free for the verified tenant at the start and no competing record wins that ID. #178 selects the expected ID and owns the command outcome. The tenant transaction manager supplies the database observations and carries out finalization. The claim writer stages the checked record. [Delivery scope and acceptance criteria](https://github.com/samovers/OFARM2/issues/178)

The **eight-hour cap applies to the claim ID check alone**, including its tests and review. This high-risk design concerns the atomic outcome of one command. The rest of #178 requires its own planning and approval within this PR. The check may observe one key and allow the already authorized insert to proceed or require the attempt to stop. Permission to submit, claim validity, other #51 checks, disclosure and replay policy stay with their existing owners. Saving a pending claim records what was submitted.

## What the database can guarantee

The database has one immediate primary key, `kernel_record_pkey`, on the tenant and record ID across all record types and lanes. Records are append-only. Both ordinary roles, `ofarm_app` and `ofarm_worker`, can stage a record before allocating their batch. The database checks the link to that batch at commit. An uncommitted row is invisible to another transaction’s ordinary lookup even when that transaction holds the tenant write lock. [Primary key and batch link](../../kernel/migrations/0001_initial.sql#L1729-L1747) · [Role privileges](../../kernel/migrations/0001_initial.sql#L5515-L5526)

Use #51’s optimistic rule for this key. A fresh read can establish that the ID is free among committed records. The exact insert is the database’s final comparison. If another transaction has staged the same key, PostgreSQL can wait or abort. If the other writer commits, our insert cannot succeed. If it rolls back, our insert can succeed. Once our insert succeeds, the unique key protects our row until our transaction ends. With append-only records, a competitor cannot commit this ID between the starting observation and our successful insert and then remove it. This accounts for the whole interval on every successful path. The two reads supply #51’s required evidence before the domain verdict. No later commit receipt is an input to either read. Success is reported only on the coordinator’s durable outcome. [Pinned #51 contract](https://github.com/samovers/OFARM/blob/538d04075881b885ed370d14326acfab7aaf429e/03_machine_contracts/drafts_non_default/authorization_finalization_evidence/protected_state_evidence/PROPOSAL.md#L9-L23)

## Order with #425

**Delivery order.** Review #425’s transaction interface first. Base any implementation of this check on its accepted interface and the assertion-command selection it consumes. #425 belongs to #424 and owns the guarded call, its rollback protection and the manager’s exclusive commit path. #426 records one acceptance condition for #178 and uses that call once on an eligible new attempt. #173 supplies the existing tenant foundation. #425 can complete its own transaction-marker tests independently of #426. [Guarded call at the reviewed revision](https://github.com/samovers/OFARM2/blob/63442e8341ea685f6d99a151bd0317247ea15ba0/docs/rfcs/OFARM2_Guarded_Operation_Claim_Call_RFC_v0_1.md) · [Command selection](https://github.com/samovers/OFARM2/issues/427)

1. **Capture the original view.** In the first query after `BEGIN READ COMMITTED`, the manager captures the tenant challenge, PostgreSQL snapshot, backend ID and full transaction ID together. Pass only the usual two challenge fields to the existing parser. After tenant verification, bind the private capture to the verified tenant and challenge, #178’s original attempt, the independently selected storage owner and the boundary within which the writes must commit together. Both the attempt and the proof pin the same owner-produced snapshot record by reference and content digest. The ordinary binder and the connection used to investigate an uncertain commit keep their existing interface. A later connection cannot supply the starting view.
2. **Select the key and operation.** #178 decides replay or new attempt. Replay performs zero claim writes. For an eligible new attempt, use the ID in the bound intent and require the proposed record to carry that ID. The domain checker independently requires this exact absence check. #427 selects the assertion command before `begin_batch`. Selection may already hold the tenant lock. Governed batch allocation takes that transaction’s lock in any case. [Batch allocation](../../kernel/migrations/0003_tenant_knowledge_position.sql#L66)
3. **Read twice before the verdict.** Inside #425’s guarded call, with the original connection and batch, evaluate the exact tenant and ID against the captured start snapshot using the database-stamped `batch_full_xid` and `pg_visible_in_snapshot`. Then issue a **separate statement after the lock has been granted** for current committed occupancy, without the start-snapshot filter. An occupied key at either check stops staging. Use the #51 absence predicate for the proposed assertion ID. For each observation independently, take the SHA-256 digest of the same canonical JSON array containing the version label `ofarm2.kernel_record.occupancy.v1`, storage owner, atomic boundary, tenant, predicate digest and observed count, in that order. Both counts must be zero. The snapshot’s `guardVersion` must equal the proof’s `snapshotVersion` and `observedVersion`. [Pinned #51 checker](https://github.com/samovers/OFARM/blob/538d04075881b885ed370d14326acfab7aaf429e/04_implementation_and_conformance/conformance_runners/preverdict_protected_state_evidence/verify_state.py#L346-L351)
4. **Stage and finish once.** Only after a passing domain verdict may the writer insert the checked assertion. Classify a duplicate-key error (`23505`) as a claim ID conflict only at that assertion’s own insert, when the statement binds the verified tenant and #178’s proposed ID and the database identifies `ofarm.kernel_record` and `kernel_record_pkey`. The write being attempted supplies the tenant and ID. The constraint name alone cannot identify which record failed. Preserve the original integrity error for a duplicate from a supporting record, another key or an insert whose origin cannot be established. A duplicate during claim staging never selects command replay.
5. **Verify ownership and finish.** Inside #425’s rollback protection, #178 reads back the staged claim on the original connection to confirm that the exact tenant and ID belong to this attempt’s batch and full transaction ID. A mismatch forces rollback. Keep the transaction, tenant lock and unique-key protection through commit or rollback. A deadlock (`40P01`) or lock timeout fails the attempt. A failed write ends the attempt without retrying inside that transaction. After a known rollback no writes from that attempt survive. If the commit response is lost, #178 reports an uncertain outcome and uses its existing recovery path.

## What is trusted and what must be tested

The protected assets are the tenant’s record ID, the original attempt’s snapshot and the truth of the reported save result. Trust the verified binding, the database’s row visibility, constraints and transaction state, and the coordinator’s independently selected intent, storage owner and atomic boundary. A request, writer return value, copied proof, session ID or caller-supplied flag cannot establish those facts. No existing database column by itself provides either logical owner reference. Live use requires trusted selections tied to this physical transaction. If the production adapter cannot obtain both references, it must refuse the check. Privileged database administration and compromised deployed code are outside this check.

These are acceptance cases at the real guarded claim entry point. #178 owns the check and its outcome assertions. #425 supplies its existing rollback and finalization behavior. Use a fresh independent observer to verify committed rows and their owning batch.

| Promise | Case and required observation |
| --- | --- |
| The key is exact and tenant-scoped. | An ID held at the start, including by another record type or lane, causes zero inserts. The same ID in another tenant does not cause refusal or disclose that record. A different ID in the proposed record stops staging. |
| The evidence belongs to the original attempt. | Swap the snapshot reference or digest, attempt, storage owner or atomic boundary, or reuse it after pool checkout or a recovery reconnect. Each stops staging. A forged or changed predicate or version also stops staging. |
| A lock wait gets a fresh read. | With a competitor that took the lock first, a committed insert produces a refusal before insert. A rolled-back insert permits one insert if the remaining checks pass. |
| An insert before the lock cannot produce two winners. | On the provisioned schema, use both ordinary roles and include a competitor that stages the key before allocating its batch. An empty fresh lookup is possible. Check that at most one transaction commits that key, the losing attempt has no saved effect or success result, and the outcome agrees with the actual winner. Exercise duplicate-key, deadlock and timeout handling without assuming which session PostgreSQL aborts. |
| A duplicate identifies the write that failed. | For the positive case, require a claim ID conflict when the checked assertion’s own insert loses on the exact tenant and proposed ID. For the supporting-record case, start with a free claim ID and a different, already committed validation-record ID in that tenant. Let the claim insert succeed and the subsequent validation-record insert in the same batch hit the same primary key. Require the original supporting-record integrity error and rollback. A fresh observer must find the existing record intact, zero new claims or supporting records from that batch, and no successful command result. |
| Ownership lasts through finalization. | A second writer trying the key after our insert cannot commit it while ours is pending. Exercise both commit and rollback, verify the winner, and fail closed on wrong-batch readback or an error caught after staging. Losing the commit response must report uncertainty until #178 verifies the outcome. |

**Evidence already observed.** Two one-off probes ran as `ofarm_app` on disposable PostgreSQL 17.10 with all eleven tenant migrations and the standard two-second timeout. A third connection confirmed the lock wait and the winner’s transaction and batch. In the commit case the fresh read found one row, the waiting writer attempted zero inserts and only the competitor’s pending claim remained. In the rollback case the fresh read found zero, the waiting writer inserted once and only its pending claim remained. The role could run `pg_current_snapshot()`, `pg_current_xact_id()`, `pg_backend_pid()` and `pg_visible_in_snapshot(xid8, pg_snapshot)`. The probes used test owner and boundary references. The insert-before-lock case was observed in the reviewer’s simplified PostgreSQL 16 model and remains to be verified on the provisioned schema. [Prior review](https://github.com/samovers/OFARM2/pull/426#issuecomment-6983714784)

## Size limit and separate locking proposal

Expected implementation areas are the private first-query capture in [the tenant manager](../../kernel/tenant_uow.py), #178’s bound claim adapter, and focused cases alongside [the transaction concurrency tests](../../kernel/tests/test_postgresql_tenant_uow_concurrency.py). Reuse #425’s staging method and rollback protection. Review any change to the pinned facade, constructor or slots with the [architecture checker](../../conformance/rewrite_architecture_check.py) and its [drift tests](../../kernel/tests/test_rewrite_architecture_check.py). At the inspected base the manager uses 579 of 600 lines and the transaction group uses 1,247 of 1,280. #425 proposes its own counted module and group limit. Recheck actual headroom after #425. Count any private helper within its owning limit. If this slice needs a higher ceiling, another trust boundary or more than eight hours, stop and return with a revised proposal.

**Conditional, separate database proposal.** #51 permits optimistic conflict detection for this ID. If the provisioned-schema case shows a conflicting commit can escape it, or the required guarantee becomes refusal *before* any competing row can be staged, stop this slice. The database migration owner would separately propose requiring an existing governed batch for the same tenant and full transaction before any ordinary-role record insert can take the unique key. Its own acceptance cases would cover both roles, record-first refusal, permitted batch-first writes and tenant isolation. That proposal requires its own review and estimate outside this cap.
