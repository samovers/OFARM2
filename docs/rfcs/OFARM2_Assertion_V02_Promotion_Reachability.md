# A pending assertion and its promotion proof must commit together

Phase A for [delivery #429](https://github.com/samovers/OFARM2/issues/429). The trust boundary is **database migration and deferred ledger integrity**. A first save records that someone submitted a claim for review. At the end of that transaction, the database must be able to follow one promotion link from the trace to that assertion. The truth of the claim remains for review. [First-save design](https://github.com/samovers/OFARM2/pull/423)

## The gap and the proposed check

The current deferred record trigger requires a `PROMOTION_EMITS` edge for v0.1 assertions, semantic event envelopes, review decisions and accepted consequences. Its list omits `ofarm.assertionrecord.v0.2`. The existing edge trigger checks the trace kind, its destination reference and both endpoints' batch and full transaction ID. The tenant-qualified keys and the unique index on promotion destinations already prevent a dangling endpoint and a second promotion edge. A missing edge never fires the edge trigger. [Current ledger rules](../../kernel/migrations/0001_initial.sql#L2035)

Add one initially deferred `AFTER INSERT` constraint trigger on `ofarm.kernel_record`, selected by the exact v0.2 assertion kind. Apply it to every such row regardless of `claimState` or lane. At commit, require an incoming `PROMOTION_EMITS` edge to this record in its tenant, governed batch and database-stamped full transaction. For this assertion, its source must name the record ID as a string in the trace's `emittedAssertionRecordRefs` array. A reference in a field for an event or review decision would describe a different relationship. The existing edge validator enforces the `ofarm.promotiontrace.v0.1` source and common provenance. The existing unique index supplies the upper bound of one. Missing structural proof raises `23514`. [Trace fields](../../contracts/kernel/OFARM_PromotionTrace_schema_v0_1.json) · [Kernel reachability rule](../../KERNEL.md#the-reachability-invariant)

The migration runs as `ofarm_owner`. Migration 0001 transferred the two existing graph functions to the sealed `ofarm_graph_validator` role. The runner cannot replace those functions. Keep them attached and add the narrow v0.2 check using `SECURITY INVOKER`, fixed schema and operator resolution, and the writer's existing read access. The trigger needs no new callable interface or privilege for either tenant role. It adds no proof table and makes no writes of its own. The immutable transaction stamp, endpoint constraints and append-only guards continue to govern every insert. [Sealed function owners](../../deployment/postgresql/provisioning_specs.py#L1847) · [Writer privileges](../../kernel/migrations/0001_initial.sql#L5515)

## Existing records and cutover

1. Before using any deployment target, obtain an authorized read for that target and record its scope. In one consistent snapshot, count v0.2 assertions, those with exactly one matching edge and trace, and exceptions. Check the tenant, destination, source kind and assertion emission, and all three rows' batch and full transaction ID. Confirm that the reader can see a known ledger row. A tenant-bound observer covers only that tenant. A disposable fixture covers only the fixture. Report counts only. Unavailable or incomplete access leaves the corresponding history unknown.
2. Install a single forward migration after tenant version 11 through the existing runner. Authenticate the preceding migration history and expected catalog before accepting its protections. Acquire exclusive locks on the record and edge tables in a fixed order, then assess all tenants in the runner's `READ COMMITTED` transaction. The lock waits for earlier writers and stays held through installation and commit. A writer waiting behind the migration must meet the new rule. Lock refusal aborts the attempt and leaves the prior version usable.
3. The owner normally sees filtered rows under forced row security. Use migration 0003's owner-only inspection pattern inside one guarded statement while holding both locks. Verify that row security is enabled and forced on both tables, temporarily lift **only owner enforcement** on those two tables, verify the scan is unfiltered for both, and restore forced enforcement before leaving the statement. An error rolls back the entire change. Ordinary sessions keep their existing policies and privileges. [Earlier owner-only history check](../../kernel/migrations/0003_tenant_knowledge_position.sql#L8)
4. Refuse the migration with `55000` if any existing v0.2 row fails the same structural rule or if complete visibility cannot be established. Existing records, edges, original transaction stamps, prior migration history and the version-11 guard survive refusal. The operator retains aggregate evidence, keeps the target at version 11 and refers the case to the ledger owner for a separately approved disposition. A later insert cannot recreate the original transaction. No automatic repair, backfill, deletion or exception list is part of this migration.
5. For empty or conforming history, restore and verify both security settings, install the deferred check, verify the expected catalog and append version 12 atomically. Register the exact migration bytes, prefix and verifier identity through the existing release mechanism. Preserve the version-11 admission and grant posture at this exact successor. The provisioning classifier and conformance checks currently recognize a closed set through 11. Any independent change to what they admit, any new permission, or any need for privileged ownership transfer goes to its respective owner before that edit. Re-running the public runner must verify the installed version and report a no-op. [Migration runner](../../deployment/postgresql/migration_runner.py#L2256) · [Version checks](../../deployment/postgresql/provisioning.py#L2915)

## Who can do what

The protected assets are the original immutable ledger, the trace-to-assertion link, tenant isolation and the migration history. Trust the installed catalog, signed tenant binding, database transaction stamp and existing migration runner. Treat staged records, references, their order and the claimed scope as untrusted. The risk is that a partial save becomes permanent or that migration overlooks a tenant's old records. Database administrator or host compromise and recovery of a forked database are outside this decision.

| Owner | Responsibility |
| --- | --- |
| Database owner, #429 | Refuse an incomplete graph at commit and an incompatible history at cutover. Only the existing migration runner may apply the migration. |
| Kernel Commit Ingress, #428 | Produce the real trace, including the event, classification, gates and emitted assertion, and stage its edge. |
| Assertion writer, #422 | Validate and stage the claim, domain payload and validation trace. Its validation trace has a different purpose from the promotion proof. |
| Command coordinator, #178, and tenant manager | #178 owns admission, result, receipt and retry. The tenant manager owns commit and rollback. The database-history blocker and the eight-hour claim-ID-check cap stay with #178. |

## Acceptance on disposable PostgreSQL 17.10

Use the public migration runner and the real ledger tables. Use the signed tenant binding under **both** `ofarm_app` and `ofarm_worker`. Use fictional records to exercise storage independently of the production producer. Each ordinary-role case has a fresh authorized observer that can read an existing control row. Compare all new batch, record and edge counts, as well as the prior graph, across the transaction boundary.

| Case | Required evidence |
| --- | --- |
| Valid first save | Stage the assertion first, then its trace and edge. Also stage the edge before either endpoint. The separate observer sees zero new rows before commit and one batch, one pending assertion, one matching trace and one edge afterward. Tenant, IDs, batch and full transaction agree. Explicit rollback leaves zero new rows. |
| Missing proof | Stage the pending assertion with no promotion trace or edge. Separately stage a trace naming the assertion and omit the edge. Each case reaches `COMMIT`, returns `23514` there, and leaves zero new batches, records or edges, including any staged supporting rows. |
| Incorrect proof | Reject a different source kind, a trace omitting the assertion or naming it only as an event, a foreign-tenant endpoint, a source from another batch or transaction, and a second promotion edge. Observe the applicable check, foreign-key, isolation or unique constraint at its actual enforcement point. Preserve the prior graph. |
| Older safeguards | Repeat successful and missing-link v0.1 controls for both roles. Exercise the other three protected kinds, append-only refusal, tenant isolation, the sealed triggers and their owners. Compare ordinary privileges before and after. |
| Existing history | Run clean install, upgrade with valid v0.2 history, and upgrade with a pre-existing orphan in another fictional tenant. Compare original keys, payloads, edges, digests and transaction stamps. Refusal leaves version 11, both forced-security flags and the prior graph intact. Success records 12 exactly once. A second run verifies a no-op. |
| Writers at cutover | Hold an old-rule writer open as migration takes the table locks. A committed incomplete old write must appear in the historical check and cause refusal. A writer that starts behind a successful cutover must encounter the new deferred check. Prove no write can fall between scan and enforcement. |

The intended PR contains the tenant migration, its exact version and catalog bindings, focused database tests and their conformance inventory. This is a provisional pre-deployment decision. A future assertion format needs its own coverage before a writer selects it. A different proof representation, broader visibility or privileges, changed transaction guarantees, or a historical repair requires another decision. The first-save integration remains with [#422](https://github.com/samovers/OFARM2/issues/422) and its [production proof producer](https://github.com/samovers/OFARM2/issues/428).
