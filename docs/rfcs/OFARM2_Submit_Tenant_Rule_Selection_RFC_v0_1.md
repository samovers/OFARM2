# Recording one farm’s rule choice for Submit

Phase A design for [OFARM2 #430](https://github.com/samovers/OFARM2/issues/430), 19 November 2026. The trust boundary is **tenant command RuntimeBundle selection control**. An authorized setup may select one already sealed bundle of rules for one farm and the fixed Submit command. Its sole durable effect is an immutable selection and the governed batch that records who made it and when it entered the farm’s ledger. This design assumes pre-deployment development. Submit setup is currently unavailable.

## What Save draft already establishes

On main at `15f2b2109c39197617fa2d7469fe412bc5a7e2d6`, the administrator’s adapter authenticates a fixed selection document, its schema and the command binding. It checks the 16 required components in a validated RuntimeBundle and sends only its computed whole-bundle digest to a named SQL routine. PostgreSQL obtains the tenant and principal from the signed-capability binding on that connection and transaction. It checks the tenant’s seal, takes the tenant write lock and checks the context and seal again. Under the lock it either verifies the existing selection or inserts its activation batch and selection. The adapter checks the returned batch ID, position and digest before committing. ## The single setup transaction

Use the existing two records and tenant lock. A generic command argument would let a caller choose the authority. Instead, propose one dedicated setup adapter and one closed database operation, `ofarm.activate_submit_operation_claim_runtime_bundle_selection(text)`. The text argument is the whole-bundle digest computed by the adapter. The installed operation fixes the command and selection tuple. It accepts no tenant, principal, rule list, batch ID or position from the caller.

1. Require the existing dedicated selection-control login, a live protected tenant and principal binding on this backend and transaction, and `READ COMMITTED`. The control login alone supplies no farm identity. Verify the bundle is already sealed for that tenant, take the existing tenant write lock, then rederive tenant and principal and recheck the seal before reading or allocating.
2. Look up the primary key `(tenant_id, selection_binding_id)`. For a new selection, PostgreSQL generates the batch ID and request ID, records the bound principal, the selected bundle and the fixed operation `ACTIVATE_COMMAND_RUNTIME_BUNDLE_SELECTION`, and allocates the next committed tenant knowledge position. Insert the selection in the **same transaction**. Its nine fields are tenant, selection-binding ID and canonical digest, command ID, command-binding ID and canonical digest, whole-bundle digest, activation batch ID and position. The command version is bound by the versioned artifact.
3. Keep the tenant-and-bundle foreign key and the composite foreign key matching the batch’s tenant, ID, position and bundle. Add a unique constraint on `(tenant_id, selection_batch_id)` so two commands cannot claim the same activation batch. The table constraint and controller’s row policy must admit exactly the whole Draft tuple or the whole Submit tuple. Independent lists of permitted IDs and digests would admit mixed tuples. Keep forced row-level security, append-only storage and the draft-only reader. Grant execution of the new owner-run routine only to the existing controller role, using the fixed trusted search path. App, worker, publisher and controller logins receive no direct rights on the selection table.
4. For an existing row, check every fixed field, the requested whole-bundle digest, and the referenced activation batch under the lock, including the original bound principal, operation and request ID shape. An exact repeat returns the original batch ID, position and digest. An unequal or partial match refuses before allocation. After one call the adapter validates exactly one result and immediately ends the transaction. A confirmed rollback removes both inserts and consumes no position. If the commit acknowledgement is lost, the outcome is unknown. An exact new attempt by the same bound party can establish which result committed.

Trust the fixed adapter and its dedicated credential custody for component validation, the binder for identity, the publisher for prior sealing, and PostgreSQL for isolation and atomicity. The main risk is attributing another farm’s or command’s rules to Submit. The adapter verifies the command and contents. SQL independently enforces the control session, protected farm binding, fixed tuple and farm-specific seal. Compromise of the trusted adapter, dedicated credential or database administrator is outside the inherited ordinary-role threat model. [Existing custody model](OFARM_Tenant_Command_RuntimeBundle_Selection_Activation_Admission_RFC_v0_1.md#6-fixed-binding-validation)

## What #427 can read

After commitment, the farm’s bound tenant ID plus the fixed Submit selection-binding ID identify **one immutable row**. Its binding digests lead to the admitted action, protected-effect contract ID, version and digest, and result schema ID and digest through the versioned artifacts. Its batch reference proves the same tenant, whole-bundle digest and ledger position. A farm may select identical bundle bytes separately for Draft and Submit if the bundle satisfies each binding. Those choices have distinct command identities, rows and activation batches.

#427 owns the read after tenant binding and before command batch allocation, the visible tenant knowledge cut and the unit’s private cache. Today app and worker have only the Draft read routine. An absent, uncommitted or mismatched Submit choice offers no usable selection. The setup receipt confers no runtime grant and creates no assertion, command attempt or promotion. [#427](https://github.com/samovers/OFARM2/issues/427) · [Guard and selector agreement](OFARM2_Guarded_Operation_Claim_Call_RFC_v0_1.md)

## Verification cases

Use disposable PostgreSQL 17.10 and fictional farms A and B. In these examples A starts at position 7, with its approved bundle X sealed before setup. Count selections, **all** tenant activation batches independently of the selection join, and the committed tenant head from a separate observer. Snapshot Draft and farm B before each run. The figures below are expected outcomes for Submit. Historical draft checks are recorded separately. [Observed draft results](https://github.com/samovers/OFARM2/issues/430#issuecomment-6988235401)

| Case | What a reviewer must observe |
| --- | --- |
| First setup for A using X | After commit, one new Submit row and one new activation batch, both naming A, X and position 8. The batch identifies the bound party. The returned ID and position match both records. No claim record is written. |
| Exact repeat, even after an unrelated batch | With a fresh binding for the same tenant and principal, return the original batch, position 8 and X. Counts and the head immediately before the repeat stay fixed. |
| Conflict | Seal a second valid bundle Y for A with the same required components and different inert content. Request Y after X. Also try X with a different bound principal. Both refuse. Repeating X as the original party still returns the original receipt. |
| Rollback and interrupted setup | Stage both records, observe neither from a second connection, then roll back. Separately force failure after batch allocation and before the selection can persist. No row, orphan batch or position survives either case. The next valid activation may take 8. Exercise lost acknowledgement after an actual commit by repeating exactly and checking for one pair. |
| Competing setups | Preserve the control login’s one-connection limit. With one control session held, observe denial of the second login, release and reconnect. After a commit the competitor sees the original selection and its conflicting choice refuses. After rollback the competitor can make the first choice. Also hold the tenant lock with an ordinary governed writer and check the controller’s position after the lock holder commits or rolls back. |
| Missing or wrong approval | Exercise the unavailable #431 result, wrong command/version or package revision, missing #430 binding, an altered required component and a missing dependency used only by the read rule. The responsible verifier or adapter refuses. No Submit call writes. A digest alone, Draft selection, current candidate pins and a success-shaped caller object also fail. |
| Isolation and custody | Bind A while X is sealed only for B, then test an unsealed bundle, a missing or stale binding, and the wrong isolation level. Each refuses. Connect as actual app and worker roles. Both must be denied activation and direct mutation. Also check direct controller mutation, public grants, and update, delete and truncate protections in the disposable database. |
| Adapter return check | Return zero rows, two rows, a malformed batch ID, an out-of-range position or a digest other than X in isolated adapter tests. The adapter must refuse success and roll back the open transaction. |
| Provenance and Draft compatibility | Before and after upgrading a populated Draft-only database, compare the draft row, batch, digest, retry and draft read. Select the same eligible bytes in separate setup transactions for each command. Require two distinct rows and batches. Reject crossed command/binding tuples and a selection linked to another tenant, batch, position or bundle. An existing inconsistent row must be refused without repair. |

## Delivery and separate prerequisites

The proposed #430 implementation areas are the fixed selection artifact, control adapter, one additive tenant migration for the owned row constraints, policies and operation, and their mechanical checks and focused tests. The migration must preserve previously committed Draft data and leave Submit absent on upgrade. A failed migration must roll back its own changes. Replacing a committed choice requires a separately reviewed binding version. Preserve old migrations and ledger history. Fictional cases can exercise transaction mechanics. Only the genuine verified #431 release, a reviewed #430 inventory and a matching already sealed tenant bundle can satisfy the positive acceptance case.

- **Provisioning verification is a concrete prerequisite.** At migration 11 the independent verifier permits exactly two binder grants and one Execute grant for the named Draft operation. A fourth grant for Submit fails exact-set comparison. Its owner must admit the exact routine, signature, owner and controller grant in the authenticated migration transition and durable head while preserving earlier heads. #430 must consume that admission before installing the operation. [Provisioning verifier](../../deployment/postgresql/provisioning.py) · [Earlier separation of authorities](OFARM_Tenant_Command_RuntimeBundle_Selection_Provisioning_Verifier_Admission_RFC_v0_1.md)
- **Bundle publication stays with its owner.** The existing temporal governance role admits three specific identities, including the Draft binding. Compare the final inventory with the admitted carrier and catalog. Any required new role, allowed identity or publication path needs its own owner delivery before a real setup. Retaining bytes under a generic reference gives them no command authority. [RuntimeBundle roles](../../kernel/runtime_bundle.py) · [Catalog admission](OFARM_Temporal_RuntimeBundle_Catalog_Publication_Admission_RFC_v0_1.md)
