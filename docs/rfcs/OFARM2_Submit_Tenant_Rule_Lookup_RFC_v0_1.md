# Look up the signed-in farm’s choice for Submit

Phase A for [#427](https://github.com/samovers/OFARM2/issues/427). The primary trust boundary is **tenant command RuntimeBundle selection**. The lookup is read-only. On the first-save path, return one immutable, verified choice for this farm or stop before the caller allocates a save batch. A successful read supplies evidence to the coordinator. The coordinator owns the decision to save. [Agreement with the transaction guard](OFARM2_Guarded_Operation_Claim_Call_RFC_v0_1.md#authority-and-call-order)

## What each owner supplies

| Owner | Evidence or decision |

The version 2 design names `SUBMIT_OPERATION_CLAIM`, `ofarm.submission-command.operation-claim.v0.2`, version `0.2`. The action is `ASSERT_OPERATION_CLAIM`. |
| [#430 / setup design](https://github.com/samovers/OFARM2/pull/437) | The approved selection binding and its component inventory, and the immutable choice and activation batch committed together for one farm. A sealed bundle by itself supplies no choice. |
| #427 | Compare that farm’s choice with both independent bindings, verify the selected sealed bundle, and hold one result on that unit. |
| [#178](https://github.com/samovers/OFARM2/issues/178), [#425](https://github.com/samovers/OFARM2/pull/425) and [#422](https://github.com/samovers/OFARM2/issues/422) | The coordinator checks an earlier outcome and handles retries. On the new-attempt path it requests selection before allocation. The guard owns dispatch and finalization belongs to its manager. The writer validates and stages the claim. |

The protected assets are the farm’s chosen rules and the authority to select them for one save. Trust the signed binding, the governed database read and the independently issued package references. A caller can repeat requests, present foreign IDs or hashes, or ask for the other command. A compromised database owner, release producer or deployed program is outside this design. The main risk is mistaking equal bytes or an equal action name for the farm’s Submit choice. Save draft shares this action and permits a different outcome. ## Reading the choice

1. Enter `ApplicationRuntime.tenant_unit_of_work` using the ordinary app or worker login. The manager binds the principal to the database transaction. For a new attempt, #178 calls `unit.resolve_assert_operation_claim_runtime_bundle()` with no arguments. Replaying a saved result belongs to #178. [Runtime entry](../../kernel/application_runtime.py) · [Unit and manager](../../kernel/tenant_uow.py)
2. Mark selection in progress on this live unit before the first read. Call `ofarm.resolve_submit_operation_claim_runtime_bundle_selection()` on that connection. #442 owns the single-statement snapshot joining the protected farm, its selection and activation, and the visible ledger head. It checks the activation’s farm, batch ID, operation, bundle digest and position, the visible head and absence of a batch already allocated in this transaction. #427 requires exactly one row for its bound tenant with the expected selection and command fields and a valid position at or below the observed head. A missing or ambiguous row refuses. The pre-existing activation batch is setup evidence. [Reader contract](https://github.com/samovers/OFARM2/issues/442)
3. Compare the row’s selection ID and digest to #430’s approved selection document. Compare its stored command ID, binding ID and digest to the issued #431 tuple. Obtain the command version from the independently pinned binding identified by that digest and compare it with the tuple’s version. The row has no separate version field. Use #431’s verifier for both complete rules and their dependencies.

   Reconstruct the **whole sealed bundle** for this farm using the existing immutable loader. Check all retained bytes, member identities, placement, lengths and content digests, then compare the reconstructed canonical document and its digest with the sealed document and the whole-bundle digest in the choice. Within that verified bundle, match every member of #430’s **required subset** exactly once by role and identity, including its expected encoding, placement, length, digest and applicable schema reference. Other valid members are inert. They cannot supply a missing required member or choose a different rule. A caller’s hash, a fixture verdict, a newer package or the draft reader supplies no selection authority. [Bundle reconstruction](../../kernel/tenant_runtime_bundle_evidence.py) · [#430 component rules](https://github.com/samovers/OFARM2/blob/b078bb7a76d1b8cf4f3a49ca95be9d1625d62c45/docs/rfcs/OFARM2_Submit_Tenant_Rule_Selection_RFC_v0_1.md#what-must-be-approved-before-setup-can-write)
4. Check the selected action, intent and body profiles, contract ID/version/digest and result schema identity/version/digest against the consumer agreement. The merged guard requires `ofarm.protectedeffect.assertionrecord.submit.v0.1`, version `0.1`, and `ofarm.assertionrecord.v0.2`. Its RFC names `EI_OPERATION_ASSERTION_V0_2` and `OPERATION_CLAIM_BODY_V0_2`. The version 2 package design requires typed fields the earlier schemas reject. The reviewed candidate names a different contract and result. The release owners provide the final identities. Incompatible names, bytes or meaning must refuse before allocation, even with a genuine selection and valid package. A change to this agreement needs its owners’ separate review. [Guard checks](../../kernel/tenant_claim_write_guard.py) · [Typed package and original approval scopes](https://github.com/samovers/OFARM2/pull/432)
5. Before publishing, confirm the unit is active, on its owning thread, still resolving this command, able to write, and has no allocated batch. A failed final state check on the owning unit refuses, publishes no choice and makes the transaction rollback-only. Publish the full immutable binding to **one command-tagged slot** only after the checks pass. Retain the farm, selection and command bindings, activation evidence, original ledger cut, bundle and admitted rule details. The guard’s eight-field view comes only from this value. Two independent command caches could select both commands on one transaction.

## Reading again and allocating a batch

| Situation | Required behavior |
| --- | --- |
| Same command on the same live unit, already verified, before allocation | A repeat public read returns the identical object with the original ledger cut and zero additional SQL. |
| Different command on a resolved unit, or re-entry during selection by the owner | Refuse, set rollback-only and expose no binding. A caught inner refusal cannot let the outer call publish. Exercise both command orders. |
| A batch is already allocated | Public Submit lookup refuses before SQL, including a repeat call after allocation. A caught refusal by the owning caller prevents commit. |
| Private guard read | `_selected_assert_operation_claim_runtime_bundle()` returns the cached assertion binding only on its live, owning, resolved and unlatched unit. This includes the normal post-allocation guard read. All other states yield no binding. It performs no lookup, SQL, registration or state change. |
| Closed unit or returned lease | Public lookup on the closed unit refuses. A new unit starts empty even on the same connection or for the same farm. A foreign thread cannot mutate the owner’s choice, latch or lease through the selector. |

**Ordering on the supported first-save path.** The coordinator calls the selector synchronously on the owning unit and waits for success before calling `begin_batch`. The manager binds fixed operations to the same connection. Neither production operation calls back into the unit. On refusal, the existing latch prevents a caught error from allowing a later allocation. The selector checks the batch on entry and again before returning. Verify zero allocator calls for a rejected lookup on this path. [Manager’s fixed operations](../../kernel/tenant_uow.py#L559-L571) · [Allocation and selection checks](../../kernel/tenant_uow.py#L323-L386)

**What the overlap measurement showed.** Test callbacks deliberately re-entered the unit on one thread. Each inner callback started once, and both measurements stopped before SQL or a completed batch. All 64 existing selector and unit-of-work tests passed. The supported synchronous production path has no such callback. General exclusion of overlapping calls is a transaction-owner hardening follow-up if a supported caller later shares a live unit or introduces re-entry. Such a caller would need review before use. #427 has no dependency on a new allocation interlock.

## Verification and limits

Use both ordinary session identities through the shared runtime entry point. For every pre-batch refusal on the owning unit, count allocator and writer calls from before the read and require zero. Check the unit has no batch, its private accessor is empty, and a subsequent allocation still fails after the caller catches the error. A normal exit after the caught refusal must report `TRANSACTION_FAILED`. Compare **all** batch counts, selection counts and farm ledger heads before and after using independent observers with a known visible committed row. For an intentionally preallocated batch, require rollback of that batch and zero further allocations. [Existing PostgreSQL checks](../../kernel/tests/test_postgresql_tenant_command_runtime_bundle_selector.py) · [Unit lifecycle checks](../../kernel/tests/test_tenant_uow.py)

| Case | Required evidence |
| --- | --- |
| Missing binding, missing reader permission, absent or uncommitted choice, foreign farm | Failed tenant binding yields no unit. A bound ordinary caller receives the same opaque selection refusal for a missing or invisible choice. Putting identical sealed bytes on both farms cannot turn the other farm’s choice into a local one. |
| Draft-only or conflicting details | Use the same action and bundle with the draft command. Separately vary one selection pin, activation link or position, command revision, component byte, contract digest, schema digest or package admission. Each stops before allocation. A fresh draft read still returns the original draft evidence. |
| Approved bundle with an extra inert member | In a fresh setup, seal a bundle with all required members and one additional allowed member. Record its actual whole digest through #430. Both roles must accept that choice and select the same approved Submit rule. Changing the extra member under the old whole digest must refuse. In a separate verifier fixture, remove a required member while leaving its bytes under an unrelated identity. That also refuses. |
| Ordering and cache | Observe the completed selection before the first allocator entry on the synchronous success path. Count zero allocator calls after refusal and zero reader calls for a public lookup after allocation. Test selector re-entry, a batch found at the final state check, a foreign selector call, independent units, repeat reads, both switch directions, rollback-only, closure and pooled connection reuse. |
| Genuine positive | Use an independently issued #431 package compatible with the consumer, a bundle sealed for this farm, and the selection committed through #430. Both ordinary roles must read the same activation and exact admitted rules. Reading alone must leave the batch count unchanged. When #178 wires the actual guard operation, its projection must read this unit’s cache, and an empty cache must produce zero dispatches. |

The smallest eventual implementation is the two named methods, one tagged selection state and a fixed verifier on the bound unit, with the focused unit, PostgreSQL and architecture checks. Preserve the draft pins and its read path. Keep the production writer factory closed. This design is provisional. The #427 selector owner tracks compatibility here until #431 issues the exact package. The tenant transaction guard owner for #425 must assess any change to its accepted contract. A change to the accepted contract, schemas, intent profiles or their meaning requires a separately reviewed guard delivery for any guard change, and a new #427 decision and approval if its invariants change. Carry this trigger into the decision card. An unresolved comparison keeps Submit unavailable.

## Implementation on PR #439

Decision `OFARM2-SUBMIT-TENANT-RULE-LOOKUP-001` version 1 has development approval on this PR. The app and worker now have the fixed Submit lookup on the signed-in farm’s transaction. It uses the same slot as Save draft. Only the owning thread can publish the choice. The lookup checks for an allocated batch before reading and again before publishing. If a batch starts during a test callback, the lookup refuses and the transaction rolls back. The private guard read only returns the choice already held on that transaction. [Unit of work](../../kernel/tenant_uow.py) · [Ordering and cache tests](../../kernel/tests/test_tenant_uow_submit_selection.py)

On disposable PostgreSQL 17.10, both ordinary roles refused Submit when only their own farm or another farm had a draft choice. Catching the error still prevented a later allocation. Each role also rolled back a batch that already existed before the lookup. Verifier tests use test-only bindings to exercise the required components, the whole-bundle digest, incompatible command fields and the guard projection. [Database cases](../../kernel/tests/test_postgresql_tenant_command_runtime_bundle_selector.py) · [Verifier cases](../../kernel/tests/test_tenant_submit_runtime_bundle_selector.py)

The production lookup refuses until its fixed package reader can authenticate #430’s selection document and consume #431’s independently verified release. The consumer comparison still needs the exact contract and schema references, versions, digests, body pointer and compatible typed fields. Matching names alone cannot establish that agreement. #442 owns the SQL function and permissions. The three deliveries are still required for a genuine successful read.
