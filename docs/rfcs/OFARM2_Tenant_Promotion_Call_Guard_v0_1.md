# Roll back the tenant transaction after a caught promotion error

[Delivery #435](https://github.com/samovers/OFARM2/issues/435) blocks [the promotion producer, #428](https://github.com/samovers/OFARM2/issues/428). Its primary trust boundary is **tenant transaction ownership and finalization**. A farmer's pending claim and the evidence that sent it to review must survive or roll back together. The [existing claim guard](OFARM2_Guarded_Operation_Claim_Call_RFC_v0_1.md) ends when claim staging returns. A later Python error can leave PostgreSQL ready to commit. The caller can catch that error and exit the tenant block normally. The [manager](../../kernel/tenant_uow.py) then commits unless it has recorded a failure.

## Who controls the call

| Owner | Responsibility |
| --- | --- |
| Tenant transaction manager, #435 | Own the lease, thread, signed tenant and principal binding, allocated batch, full transaction ID, single-use dispatch, rollback-only flag and finalization. Retain the exact checked claim returned by this unit. |
| [Coordinator, #178](https://github.com/samovers/OFARM2/issues/178) | Own admission, new attempt versus replay, and availability and ordering of the complete operation before staging. For a new eligible submission, call the guard with the original inputs. Own the command outcome, retry and receipt. |
| [Claim writer, #422](https://github.com/samovers/OFARM2/issues/422) and [existing guard, #424](https://github.com/samovers/OFARM2/pull/425) | Stage and check the assertion and its protected-effect evidence. The new call can use only the successful return from the current unit. |
| [Commit Ingress, #428](https://github.com/samovers/OFARM2/pull/433) | Verify admitted sources and gate evidence, construct and insert one trace and one link, read both back, and compare the stored identity and digest with the independently expected binding before returning. Source owners decide whether their evidence is admissible. [Producer contract](https://github.com/samovers/OFARM2/blob/3bb6ce396c968d4d9389897216f927c2bb7a6d04/docs/rfcs/OFARM2_Pending_Claim_Promotion_Evidence_v0_1.md#a-caught-failure-must-prevent-commit) |

Protect the original claim, promotion evidence, and isolation of other leases against malformed inputs, out-of-order, duplicate, stale and foreign-thread calls, and an ordinary caller that catches exceptions. Trust the binder, manager, fixed producer composition and database. A compromised runtime, arbitrary in-process code execution or database administrator is outside this model. Database enforcement stays with [#429](https://github.com/samovers/OFARM2/issues/429).

## From claim staging to finalization

1. On opening a unit, bind the private promotion operation to the same leased connection and signed context as the claim operation. The ordinary application and worker factories leave it unavailable until separately governed composition supplies the real producer. The public manager and runtime accept no producer override. Bind once. Skip promotion on replay in the coordinator.
2. Remember the exact immutable result only after the existing `stage_operation_claim` has succeeded, including its final checks. Add one fixed synchronous method on the existing tenant unit, `promote_pending_claim(inputs)`. Its argument carries inert producer inputs. It takes no claim result, callback, connection, SQL, success flag or transaction control. An equal-looking result from a caller or another lease cannot establish eligibility. Existing claim-only callers keep their provisional return and finalization contract.
3. Check that the receiver is active and on its owning thread before touching any unit state. For an owning call, enter the rollback-only protection **before** checking writability, the presence of the operation, the staged result, or the inputs. Consume the callable once before invoking producer code, including any projection or input validation that could re-enter. Compare the transaction bindings in the attempt to the manager's own signed tenant, principal and lease nonce, active assertion batch, request, selected command/bundle and full transaction ID. Supply the retained checked claim and original batch to the bound operation. All producer-input construction that can refuse belongs inside this call. No fallible preflight in the caller after staging can stand in for it.
4. On that same connection, the bound operation performs #428's input checks, trace and edge writes, and final physical readback. #428 owns the comparison of actual and expected evidence. The guard checks the narrow return contract (a checked trace ID and digest in the agreed form) and rechecks writability after dispatch and before releasing the result. A caught inner call still makes the outer call fail. A good return is provisional.
5. Any `BaseException` on the live owning call sets the unit's **existing** rollback-only flag before the original error is re-raised. Calling early, on an unavailable operation, twice, or re-entering has this effect. Further owner writes refuse. Stale or foreign-thread calls are refused before dispatch and cannot mark a healthy owner rollback-only. Closing the unit drops both the operation and staged-result reference, including when a pooled connection is reused.
6. On normal exit with the flag set, the existing manager rolls back or discards the connection, returns `TRANSACTION_FAILED` and makes **zero native COMMIT calls**, even if a savepoint restored `INTRANS`. An exception that escapes the block uses existing rollback handling. After a valid provisional return only the manager may commit. Loss of a commit reply keeps the existing `FINALIZATION_UNKNOWN` outcome and recovery ownership. The guard never repeats dispatch. [Finalization rules](OFARM2_Tenant_Transaction_Failure_Handling_RFC_v0_1.md) · [Uncertain commit recovery](OFARM2_Physical_Transaction_Outcome_Recovery_RFC_v0_1.md)

Use the existing unit's closed state, checked return and rollback flag. A check of PostgreSQL status alone misses a caught Python failure and a recovered SQL error. A new finalizer or a second durable status record would give two owners the same decision. Keep the facade and manager wiring in `kernel/tenant_uow.py` and the narrow fixed operation in the counted tenant guard code. Extend the [existing architecture checks](../../conformance/rewrite_architecture_check.py) and [drift tests](../../kernel/tests/test_rewrite_architecture_check.py) for the exact facade, slots, private factory, constructor, fixture reachability and file/group limits. Keep each affected module in the measured budget and document any measured adjustment in review.

## Proof under both tenant roles

Run **every row** separately as `ofarm_app` and `ofarm_worker` on disposable PostgreSQL 17.10 with the real signed binder, allocator, manager and finalizer. Only a test-side manager subclass binds the fixed operations. Give each attempt a unique batch and distinguish the claim, trace and link markers. Check the signed role and tenant, backend PID and full transaction ID at allocation, staging, producer dispatch and final readback wherever that phase is reached. Separately open and bind a fresh connection with the original ordinary role and tenant. It must see a precommitted control each time it counts the exact attempt's batch and markers. Before finalization, the observer sees none of the provisional rows. Count actual driver COMMIT attempts on the original lease.

| Case | Required observation |
| --- | --- |
| Caught refusal before the producer writes | Stage the claim marker. Refuse an input inside the guarded call, catch the original error **inside** the tenant block, and exit normally. The writer can still see the earlier marker and PostgreSQL reports `INTRANS`. The manager reports `TRANSACTION_FAILED`, makes zero COMMIT calls, and the observer sees zero new batches or markers. |
| Caught failure after writes | Insert both promotion markers, then raise during readback. Exercise an ordinary Python exception, a process-control exception (check original identity), and an invalid return. Catch inside and exit normally. Prove the writes ran on the original backend before failure. Require the same manager outcome, zero COMMITs and zero durable rows. |
| Caught SQL error, including recovery | Stage the claim before a fixture savepoint. Cause a genuine SQL error inside the producer. Exercise both the failed transaction and rollback to the savepoint after catching the error inside the block. For the recovered case prove `INTRANS` and earlier claim visibility before normal exit. Both paths must report `TRANSACTION_FAILED`, make zero COMMIT calls and leave zero durable rows. Only the test harness may manipulate this savepoint. |
| Order, binding and single use | Before successful staging, with an unavailable operation, or with mismatched tenant, principal, nonce, request, batch, full transaction ID, action or bundle, require zero producer writes. Repeat after success, and re-enter from within the producer while swallowing the inner refusal. Each owning failure is terminal and the observer sees zero durable output. A duplicate cannot dispatch twice or produce a successful outer return on re-entry. |
| Healthy owner and later lease | Try a foreign thread while the owner is active, and a closed unit after the same backend is leased again. Neither may dispatch or alter the healthy owner's outcome. The legitimate owner can finish and commit its own exact batch and markers once. With production's default factory, prove zero producer dispatches. |
| Commit, explicit rollback and uncertain result | A valid return permits one original COMMIT and exactly one of each expected row afterwards. An exception after that same return rolls everything back. Exercise a lost commit reply with the existing outcome harness and confirm no second dispatch. |

The marker tests establish transaction-owner behavior. #428 must repeat commit, rollback and caught errors with the real trace and link. #178 must exercise its actual coordinator. This provisional change adds no route, role, migration, authority to select evidence, or production activation. If readback needs a second lease, a caller-chosen producer, or different recovery semantics, stop for a revised design. Next, implement the guard and run the two-role matrix only after approval of this separate Delivery PR.
