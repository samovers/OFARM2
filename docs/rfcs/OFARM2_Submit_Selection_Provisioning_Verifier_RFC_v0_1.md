# Verifying the PostgreSQL permission for Submit setup

Phase A for [OFARM2 #438](https://github.com/samovers/OFARM2/issues/438). Proposed decision `ISSUE438-SUBMIT-SELECTION-PROVISIONING-001`, version 1. The trust boundary is **PostgreSQL provisioning verification**. On main at `642c8f7f3eba66cb1d7cf41ef65e62f29f24c2d9`, the selection controller has three routine grants at tenant migration 12. A fourth produces a provisioning difference. This design would let the verifier recognize one specific fourth grant and report any mismatch. Submit is unavailable.

## What the verifier trusts

The protected assets are the controller's permissions and the migration history that explains when they may exist. The risk is accepting a plausible function or grant before its migration, or overlooking another party with execution rights. Recognition requires both the exact migration evidence and the exact PostgreSQL catalog state.

A caller, environment setting or test helper cannot select a transitional posture. A compromised database superuser, server or release authority is outside this verifier's trust model. Verification executes no activation function.

## The catalog comparison

1. Keep the exact cross-schema family comparison for the controller, the control login and `PUBLIC`. The first two grants are `ofarm_binder` granting the controller `EXECUTE` on `ofarm.create_tenant_challenge()` and `ofarm.bind_tenant_capability(text)`. The third is `ofarm_owner` granting the controller `EXECUTE` on `ofarm.activate_commit_operation_claim_draft_runtime_bundle_selection(text)`. All have grant option false. Add the fourth row only in the two Submit postures. Preserve explicit ACLs across schemas and effective default `PUBLIC` execution for non-system routines (OID at least 16384). PostgreSQL represents `PUBLIC` as grantee OID zero. [Existing ACL observations](../../deployment/postgresql/provisioning.py#L3502-L3658)
2. Inventory **every** routine named `activate_submit_operation_claim_runtime_bundle_selection` across namespaces and overloads, regardless of grants. Where Submit is required, exactly one row must describe `ofarm.activate_submit_operation_claim_runtime_bundle_selection(text)`, with the single built-in `pg_catalog.text` input type, function kind (`prokind = 'f'`), `proowner = ofarm_owner` and `prosecdef = true` (runs as its owner). Compare the owner directly. Where Submit is absent the inventory must be empty. #430's structural verification owns the body, trusted search path, return contract and other migration-owned structure.
3. For that exact function expand its effective ACL, including PostgreSQL's default when `proacl` is null. Compare **all** non-owner rows. The only allowed tuple is grantee `ofarm_command_runtime_bundle_selection_controller`, grantor `ofarm_owner`, privilege `EXECUTE`, grant option false. Checking effective access for a single role would miss an extra grant. The dedicated `ofarm_command_runtime_bundle_selection_control_login` inherits its sole controller membership with `INHERIT TRUE / SET FALSE / ADMIN FALSE` and connection limit 1. A direct grant to the login is drift. Preserve Save draft's own routine inventory and arbitrary-grantee check in every state. [Save draft SQL and grant](../../kernel/migrations/0008_tenant_command_runtime_bundle_selection.sql#L300-L308) · [Granted roles and membership](../../deployment/postgresql/provisioning_specs.py#L2039-L2099)

## Order of operations and recovery

1. `verify_service` remains the fresh-target check. For a migrated target the ordinary read-only preflight is `verify_service_infrastructure`. It observes a consistent snapshot. The public production runner authenticates the complete tenant release before target access, verifies the admin and migrator routes agree, starts its existing read/write transaction, takes the permanent migration lock, and assumes the fixed schema owner. It repeats stable provisioning checks and authenticates ledger structure and history on that connection. [Provisioning entry points](../../deployment/postgresql/provisioning.py#L4874-L4905) · [Lock and target identity](../../deployment/postgresql/migration_runner.py#L541-L633)
2. Only for the fixed tenant service, the exact version-12 prefix above and the agreed version-13 literal member, execute the already authenticated source on that connection. After it returns, require `INTRANS`, repeat `require_authoritative_migration_set` for the complete release, and call one private Submit-specific locked verifier before any append. The verifier rechecks the exact predecessor and all ordinary locked protections with the fourth grant required. Keep `migration_locked_differences(target, spec)` stable-only, the V8 branch exclusive to V8, and other sources on their ordinary path. No public switch, database marker or synthetic executor enters this branch. [Existing V8 ordering](../../deployment/postgresql/migration_runner.py#L2295-L2364) · [Production and test entry points](../../deployment/postgresql/migration_runner.py#L2521-L2610)
3. Any difference stops the migration. On success, recheck the protected ledger and unchanged prior history, append exactly one row through the runner, authenticate the result including its current release and execution IDs, and run ordinary locked verification on that transaction's new head. Retain the migration-owned final catalog and structural checks. Commit once. A new observer or a later verified no-op must see the same head and grants. Retry uses the original ledger evidence even if the new invocation has a fresh execution ID.
4. A refusal, exception or confirmed pre-commit disconnect rolls back the function, grant and ledger append together. A lost commit response has an unknown outcome. Reconnect, take the lock and verify which complete state survived before retrying. A mixed state reports drift and receives no repair. [Runner commit and no-op behavior](../../deployment/postgresql/migration_runner.py#L2171-L2207)

## Disposable PostgreSQL verification plan

Use the existing tenant provisioning and migration fixtures on PostgreSQL 17.10. Start each case from a known disposable target with the fixed login settings. Record the ordered ledger rows, all controller-family grants, both activation inventories and both sets of non-owner grants from a separate connection. At the transition, record the same facts inside the runner transaction and compare them with the observer. Use fictional release labels and fresh test UUIDs. The following are acceptance cases for later implementation.

| Change one condition per case | Required observation |
| --- | --- |
| Exercise each historical state above, the V8 transition, and a released head newer than the local verifier knows | Each supported state passes its original checks. Inject an early Submit name with owner-only ACL, then the proposed controller ACL. Both refuse on stable paths. Applying migration 12 takes the ordinary locked path. A version 13 with a different filename or predecessor misses the Submit branch. A later head also refuses. |
| From the agreed version-12 prefix, run #430's exact version 13 through the public runner | The post-source check sees the old ledger and four grants. The ordinary locked check on that same snapshot reports a difference. The observer sees three and no new row. After commit, both ordinary routes pass with four and one new row. A second run applies zero migrations. |
| Move or remove the function, substitute another input type or owner, add an overload or a second schema copy, use a procedure or an invoker function | Each changed inventory refuses independently on the transitional and committed shapes. The early owner-only case must fail even when the global grant set is otherwise exact. |
| Remove the controller grant, substitute its grantee or grantor, enable grant option, or add `PUBLIC`, the login, app, worker or a different role | Require the observed non-owner row difference for each case, including a default `PUBLIC` ACL. For a delegated grant, record the actual grantor PostgreSQL stored. Pair the live case with a single-field tuple test if the server also requires a supporting grant. Add a family grant on an unrelated routine to exercise the global scan. |
| Drop a binder or Save draft grant, add a Save draft grantee, alter membership options or change the login limit | Each reports the corresponding historical difference even with an otherwise exact Submit function. Restore the fixture and require the original inventory to pass. |
| Change one source byte under its old name, or change the protected history or service | Complete-release authentication refuses altered bytes before connection. Force branch-local reauthentication to refuse after source execution and observe rollback before append. Exercise missing/stale/wrong predecessor, missing/duplicate/gapped/extra version, wrong filename, hash, length, prefix, service or spec digest, and an otherwise correct new row with a substituted earlier row. Each refusal occurs on its owning route. The audit service, synthetic executor and any pre-source or post-append invocation have no Submit transition. |
| Stop after source, then separately after append but before commit. Also drop the acknowledgement after a successful commit | After confirmed rollback a fresh observer finds the original ledger, three grants, no Submit function and an ordinary verification pass. After a lost acknowledgement the committed case yields one new row, four grants and a verified no-op. Prior ledger rows and Save draft grants match their before values throughout. |

While the literal release ends before Submit, a test-local release binding and inert function can exercise catalog comparisons and transaction ordering on a disposable target. Keep this wiring in the test process. The unmodified production entry must reject those fictional bytes. Only #430's eventual reviewed source and literal release can supply an end-to-end positive through the unmodified runner and its final structural verifier. The existing suites already cover historical release projections, grant comparisons, the stable-versus-transitional V7 observation, V8 reauthentication rollback and the authoritative tenant no-op. ## Delivery decision

This draft adds one durable design. After semantic approval, the smallest verifier change belongs in `deployment/postgresql/provisioning.py`, the one locked call site in `migration_runner.py`, their focused tests, and the mechanical test inventory if its cases change. Reuse the existing classification, grant comparisons and runner. A global fourth-row allowance would accept an early grant. A second migration registry would duplicate the source of release identity. The historical decisions and migration sources retain their original meaning.

This is a pre-deployment proposal. A changed permission, owner, migration ordering that alters the approved transition, new write or repair authority, broader release family, different delivery PR or deployment posture requires renewed review and a decision from the relevant owner. Next, obtain semantic approval in the #438 chat for verifier development in draft PR #441. The agreed successor can pass the production verifier only when #430 supplies its reviewed migration bytes and literal release entry. #431's verified binding and #430's own acceptance govern eventual Submit availability.
