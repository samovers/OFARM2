# A pending assertion and its promotion proof must commit together

RFC v0.3 corrects the visibility tests for the proposed migration on draft #434. [Phase A re-review, B2](https://github.com/samovers/OFARM2/pull/434#issuecomment-7002429294)

Phase A for [delivery #429](https://github.com/samovers/OFARM2/issues/429). The trust boundary is **database migration and deferred ledger integrity**. A first save records that someone submitted a claim for review. At the end of that transaction, the database must be able to follow one promotion link from the trace to that assertion. The truth of the claim remains for review. [First-save design](https://github.com/samovers/OFARM2/pull/423)

## The gap and the proposed check

The current deferred record trigger requires a `PROMOTION_EMITS` edge for v0.1 assertions, semantic event envelopes, review decisions and accepted consequences. Its list omits `ofarm.assertionrecord.v0.2`. The existing edge trigger checks the trace kind, its destination reference and both endpoints' batch and full transaction ID. The tenant-qualified keys and the unique index on promotion destinations already prevent a dangling endpoint and a second promotion edge. A missing edge never fires the edge trigger. [Current ledger rules](../../kernel/migrations/0001_initial.sql#L2035)

Add one initially deferred `AFTER INSERT` constraint trigger on `ofarm.kernel_record`, selected by the exact v0.2 assertion kind. Apply it to every such row regardless of `claimState` or lane. At commit, require an incoming `PROMOTION_EMITS` edge to this record in its tenant, governed batch and database-stamped full transaction. For this assertion, its source must name the record ID as a string in the trace's `emittedAssertionRecordRefs` array. A reference in a field for an event or review decision would describe a different relationship. The existing edge validator enforces the `ofarm.promotiontrace.v0.1` source and common provenance. The existing unique index supplies the upper bound of one. Missing structural proof raises `23514`. [Trace fields](../../contracts/kernel/OFARM_PromotionTrace_schema_v0_1.json) · [Kernel reachability rule](../../KERNEL.md#the-reachability-invariant)

The migration runs as `ofarm_owner`. Migration 0001 transferred the two existing graph functions to the sealed `ofarm_graph_validator` role. The runner cannot replace those functions. Keep them attached and add the narrow v0.2 check using `SECURITY INVOKER`, fixed schema and operator resolution, and the writer's existing read access. Explicitly revoke `EXECUTE` from `PUBLIC` on the new trigger function in the migration transaction. Verify its effective privileges for both tenant roles. Each role can fire the trigger by inserting a record using its existing permissions. The immutable transaction stamp, endpoint constraints and append-only guards continue to govern every insert. [Sealed function owners](../../deployment/postgresql/provisioning_specs.py#L1847) · [Writer privileges](../../kernel/migrations/0001_initial.sql#L5515)

## Existing records and cutover

1. Before using any deployment target, obtain an authorized read for that target and record its scope. In one consistent snapshot, count v0.2 assertions, those with exactly one matching edge and trace, and exceptions. Check the tenant, destination, source kind and assertion emission, and all three rows' batch and full transaction ID. Confirm that the reader can see a known ledger row. A tenant-bound observer covers only that tenant. A disposable fixture covers only the fixture. Report counts only. Unavailable or incomplete access leaves the corresponding history unknown.
2. Install a single forward migration after tenant version 11 through the existing runner. Authenticate the preceding migration history and expected catalog. Lock the record table and then the edge table in `ACCESS EXCLUSIVE` mode. Assess all tenants after both locks are held in the runner's `READ COMMITTED` transaction. Hold both locks through commit. An edge-first writer can already hold the edge table while it waits for the record table. A deadlock or lock timeout can abort either transaction. A failed migration rolls back its catalog and history changes. A failed writer rolls back all of that save. A writer proceeding after migration commit must meet the version-12 rule.
3. The owner normally sees filtered rows under forced row security. While holding both locks, use one guarded statement to verify that row security is enabled and forced on both tables, temporarily lift forcing for their owner, check visibility, scan history, and restore forcing. Make the visibility check a single self-contained, labelled PL/pgSQL block immediately before the scan. It must find both named tables, `ofarm.kernel_record` and `ofarm.kernel_edge`, confirm that `current_user` is `ofarm_owner` and owns both, and check each table separately. Row security must be enabled, its force flag must be clear, and `pg_catalog.row_security_active(oid)` must return false for that table in this session. If any condition cannot be confirmed, raise `55000` with a visibility-specific diagnostic before reading ledger rows. An error rolls back the entire change. Ordinary sessions keep their existing policies and privileges. [Earlier owner-only history check](../../kernel/migrations/0003_tenant_knowledge_position.sql#L8) · [PostgreSQL visibility check](https://www.postgresql.org/docs/17/functions-info.html)
4. Refuse the migration with `55000` if any existing v0.2 row fails the same structural rule or if complete visibility cannot be established. Existing records, edges, original transaction stamps, prior migration history and the version-11 guard survive refusal. The operator retains aggregate evidence, keeps the target at version 11 and refers the case to the ledger owner for a separately approved disposition. A later insert cannot recreate the original transaction. No automatic repair, backfill, deletion or exception list is part of this migration.
5. For empty or conforming history, restore and verify both security settings. The runner installs the check, appends version 12, verifies the expected catalog and commits the transaction. Recognizing **this exact version 12** is in scope. Update the migration set and catalog identity, the provisioning classifier, the conformance checks, and the version expectations in readiness and test fixtures. Match the exact filename, byte length, source hash, prefix digest, service and provisioning specification. Keep all earlier checks and use the same version-11 role and admission settings at version 12. An unrecognized successor still refuses. A second run of the public runner must report a verified no-op. A change to who may act or what they may access requires its own owner. [Migration runner](../../deployment/postgresql/migration_runner.py#L2256) · [Version checks](../../deployment/postgresql/provisioning.py#L2915)

## Who can do what

The protected assets are the original immutable ledger, the trace-to-assertion link, tenant isolation and the migration history. Trust the installed catalog, signed tenant binding, database transaction stamp and existing migration runner. Treat staged records, references, their order and the claimed scope as untrusted. The risk is that a partial save becomes permanent or that migration overlooks a tenant's old records. Database administrator or host compromise and recovery of a forked database are outside this decision.

| Owner | Responsibility |
| --- | --- |
| Database owner, #429 | Refuse an incomplete graph at commit and an incompatible history at cutover. Only the existing migration runner may apply the migration. |
| Kernel Commit Ingress, #428 | Produce the real trace, including the event, classification, gates and emitted assertion, and stage its edge. |
| Assertion writer, #422 | Validate and stage the claim, domain payload and validation trace. Its validation trace has a different purpose from the promotion proof. |
| Command coordinator, #178, and tenant manager | #178 owns admission, result, receipt and retry. The tenant manager owns commit and rollback. The database-history blocker and the eight-hour claim-ID-check cap stay with #178. |

Use the public migration runner and real ledger tables for install, upgrade, refusal and no-op tests. The isolated visibility check below is additional defence-in-depth evidence. Use the signed tenant binding under **both** `ofarm_app` and `ofarm_worker` for ordinary writes. Use fictional records to exercise storage independently of the production producer. Each ordinary-role case has a fresh authorized observer that can read an existing control row. Compare all new batch, record and edge counts, as well as the prior graph, across the transaction boundary.

### How to verify visibility and rollback

Start with a version-11 fixture containing complete v0.2 graphs in two fictional tenants. From a separate authorized connection with full fixture visibility, use a consistent read-only snapshot to capture every field of every migration history row, the security flags on both tables, and the batches, records and edges for both tenants, including keys, payloads, digests and original transaction IDs.

For each isolated case, use a transaction that will roll back on the real migrator connection, assume `ofarm_owner`, confirm that identity, and take the same table locks. Set only the force flags needed for the case. From the owner's session, check the known fixture rows on each table independently. For example, when records stay forced, require that both tenants' known links are visible and their known assertions are hidden. Reverse the controls when edges stay forced. For the positive control, require both assertions and both links to be visible.

Read the labelled block from the authenticated version-12 migration bytes. Require a unique start label and matching end label, then run the enclosed block with its labels intact and its bytes unchanged as an anonymous statement. The block has no dependency on surrounding variables. The test executes only the check that follows the change to owner enforcement. The production runner always executes the whole migration. This keeps one visibility check and adds no persistent function, new grant or test switch.

After each isolated run, roll back the entire transaction. A fresh authorized reader must find both tables enabled and forced again and the entire version-11 history and both graphs identical to the baseline. For the public-runner refusal, compare to the baseline captured **after the alteration and before the run**. The deliberately changed flag must survive the refusal along with all original history and data. Verify that the same public runner and release succeed on conforming version-11 history. Record the failure phase or diagnostic that ties the refusal to the drift. An unrelated setup or connection error cannot satisfy this case. ## Provisional use and upgrade path

The version-11 ledger already supplies the proof format, unique destination, sealed edge checks and tenant-bound reads. Those facts make it possible to test the proposed version-12 rule now on disposable PostgreSQL with fictional records. Deployment history is still unknown. If the two ordinary roles cannot verify a valid graph with existing permissions, a writer can commit between the scan and enforcement, or the proof requires a different representation, stop and redesign with the responsible owner. An incompatible historical row calls for the refusal and preservation procedure above.

After both roles pass the database cases, the assertion writer can test the first save with the real Commit Ingress producer. Any later deployment requires an authorized assessment of the actual target, the locked recheck during upgrade and a release decision under independently human-controlled, verifiable approval. Each future assertion format needs coverage before a writer selects it. The review's proposals for unknown record kinds and stricter v0.1 reference matching are separate work.
