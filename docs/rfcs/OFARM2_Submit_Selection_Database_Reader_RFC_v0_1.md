# Read a farm’s committed Submit choice

Phase A for [Delivery #442](https://github.com/samovers/OFARM2/issues/442), 19 November 2026. Decision `OFARM2-SUBMIT-SELECTION-DATABASE-READER-001`, version 1. The primary trust boundary is the PostgreSQL tenant selection reader and its ordinary-role permissions. A signed-in app or worker session needs to discover which Submit rules its farm selected before it starts a save batch. The proposed database operation returns evidence of that existing choice. The only lasting changes are the installed reader, its row policy and grants, and the migration evidence for them.

The controller commits the choice and its activation batch atomically. Its receipt names the batch, position and whole-bundle digest. |

It caches the choice on the live unit of work. Batch allocation, dispatch, writing, package admission and deployment retain their existing owners. |

The protected facts are each farm’s choice, activation and ledger head, and the separation between reading and activating. An ordinary caller can choose its SQL and transaction timing. It may know another farm’s identifiers or possess identical bundle bytes. Only the binder, authenticated migration and committed setup supply authority here. Database administrator, controller or signing-key compromise is outside this ordinary-role model. A wrong farm, command or head could give a save the wrong rules. All three must agree in the same database observation.

## The call and its result

The public database entry is `SELECT * FROM ofarm.resolve_submit_operation_claim_runtime_bundle_selection()`. It accepts zero arguments. The authenticated installation fixes one selection tuple, including both canonical digests. The proposed selection ID is `ofarm.tenant-command-runtime-bundle-selection.submit-operation-claim.v0.1`. Pin its digest from #430 and the command-binding digest from #431 when available. A caller supplies no farm, command, receipt, package, position or cut. The command-binding version comes from #431’s verified tuple. [Consumer’s positional comparison](https://github.com/samovers/OFARM2/blob/737932cae7e4387c0b7b1e8e230ece7420099e8d/kernel/tenant_runtime_bundle_evidence.py#L81-L95)

| Position | Returned column | PostgreSQL type | Source |
| ---: | --- | --- | --- |
| 1 | `tenant_id` | `uuid` | Bound ID, matched to the registry and selection |
| 2 | `tenant_ref` | `text` | Registry row for that ID |
| 3 | `selection_binding_id` | `text` | Fixed #430 selection row |
| 4 | `selection_binding_canonical_digest` | `text` | Same row, matched to the approved selection digest |
| 5 | `command_id` | `text` | Same row, exactly `SUBMIT_OPERATION_CLAIM` |
| 6 | `command_binding_id` | `text` | Same row, exactly `ofarm.submission-command.operation-claim.v0.2` |
| 7 | `command_binding_canonical_digest` | `text` | Same row, matched to #431’s issued binding digest |
| 8 | `selection_batch_id` | `text` | Referenced activation batch |
| 9 | `selection_knowledge_position` | `bigint` | Position of that activation |
| 10 | `runtime_bundle_digest` | `text` | Whole-bundle digest shared by the selection and activation |
| 11 | `selection_knowledge_cut` | `bigint` | Greatest visible position across **all** batches of the bound farm |

**R1 · Bind the farm.** Require `READ COMMITTED`, `SESSION_USER` exactly `ofarm_app` or `ofarm_worker`, and the expected definer `CURRENT_USER = ofarm_owner`. Use `ofarm.current_tenant_id()` and the matching `ofarm.tenant_registry` row. The protected context binds backend PID, backend start and full transaction ID. An unbound or stale connection refuses. Another farm’s choice cannot satisfy the join. [Binder lookup](../../kernel/migrations/0001_initial.sql#L1146-L1169)

**R2 · Prove the choice and activation.** In one data-reading statement, join the bound farm to `ofarm.tenant_command_runtime_bundle_selection` by farm and the complete five-field selection/command tuple (columns 3–7). Join `ofarm.governed_write_batch` on the same farm, batch ID, knowledge position and whole-bundle digest. Require the setup operation `ACTIVATE_COMMAND_RUNTIME_BUNDLE_SELECTION` and #430’s generated selection batch and request ID shapes. Require the authenticated predecessor to enforce the immutable primary key `(tenant_id, selection_binding_id)`, tenant/bundle and composite batch foreign keys, and uniqueness of `(tenant_id, selection_batch_id)`. Together those identify at most one choice and its own activation. Missing or inconsistent evidence returns zero rows. A valid join returns exactly one. Only the control path can record the selection linking that activation. The activating party may differ from the ordinary reader on the same farm. A concurrent setup becomes visible as a complete committed pair in a later statement.

**R3 · Observe the head before allocation.** In that same statement compute `max(knowledge_position)` over every visible governed batch for the bound farm. Require `1 <= selection_knowledge_position <= selection_knowledge_cut <= 9007199254740991`. Exclude any row if a batch for that farm has `full_xid = pg_catalog.pg_current_xact_id_if_assigned()`. An assigned transaction ID from binding alone is normal. It is the matching batch row that closes reading. The selection, activation, head and exclusion share the snapshot of #439’s fixed standalone SELECT. A batch already allocated in this transaction when that statement starts disqualifies the read. A later unrelated commit can raise the cut on a fresh read while preserving the activation position. The read takes no farm write lock and allocates no batch or position. [Existing fixed read and head policy](../../kernel/migrations/0010_tenant_command_runtime_bundle_selector.sql#L58-L190)

**R4 · Give only the two logins the read.** Install one schema-qualified `plpgsql`, `STABLE`, `PARALLEL UNSAFE`, `SECURITY DEFINER` function owned by the existing `ofarm_owner`, with `search_path = pg_catalog, pg_temp` and qualified relation, function and type references. Revoke the default `PUBLIC` privilege and grant only non-grantable `EXECUTE` from the owner to each ordinary login. Add one owner-facing permissive `FOR SELECT TO ofarm_owner` policy on the selection table. Its predicate requires either exact session login, the bound farm and the complete fixed Submit tuple. Forced row security still applies to the owner. The reader repeats its fixed tuple because applicable permissive policies combine with OR. Reuse the existing owner-facing bound-farm batch policy for both the activation and the head. Keep the Save draft reader and policy, setup policies, and all underlying relation and column privileges intact. A general table grant or parameterized command lookup would let the caller choose beyond this one read. [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

## Acceptance on the real database

Use disposable PostgreSQL 17.10 with #430’s genuine migrated schema, then migrate through the real successor with the unmodified production runner. Use separately connected actual `ofarm_app` and `ofarm_worker` sessions and signed capabilities through the ordinary challenge/bind path. Observe the session and current role and bound farm before each positive. Administrator-injected bound context, fabricated rows or receipts, an inert migration, a replacement verifier or a mocked selector cannot establish this acceptance.

Use fictional farms A and B. Seal identical legitimate bytes for both, including an allowed extra inert component covered by the whole-bundle digest. Set up A through #430 with #431’s compatible issued package, retain its **committed** receipt in the test, and leave B without a Submit choice. Commit a later unrelated batch for A so the expected head exceeds the activation position. For each read, take independent before/after snapshots from a separate observer for **both** farms. Count all selection rows, count all governed batches independently of the selection join and measure the maximum batch position. Check the Draft row and receipt across migration and reading. Hold unrelated writes constant while comparing these observations.

## Delivery decision

This draft contains the design only. The smallest complete implementation on this PR is the reader migration, literal release identity, exact-head provisioning compatibility, migration-owned structural/catalog checks and focused database and interoperability tests, with mechanical test inventory updates where required. The existing binder, selection table, activation batch, head policy, runner, structural verifier and consumer each retain one source of authority. There is no generic lookup, second registry, copied package verifier or new durable farm state to maintain. The existing Draft path remains independently usable.

The proposal is provisional before deployment. Missing package, setup, schema or consumer evidence keeps the genuine positive open. A change in capability, authority, effects, invariants, successor or predecessor identity, irreversible behavior, named PR or deployment posture requires renewed review and the applicable decision. Next, obtain independent review of the draft head and a same-chat implementation decision.
