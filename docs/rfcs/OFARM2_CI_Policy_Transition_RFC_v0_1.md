## Outcome and boundary

Keep both complete baselines together. Once #411 installs the normal 60-minute policy on main, retire temporary authority and validate P itself through the normal main path before P can merge.

The one primary trust boundary is **selection, bounded use, revocation and recognition of CI evidence policy**. No change to production code, tenant or database authority, signing keys, test transport, migrations, test assertions, database lifetimes, comparison rules, dependency pins, native verifier semantics, release identity or deployment is permitted. The temporary route selects the already proposed finite 60-minute conformance envelope; it does not split jobs, tune tests or introduce retries. The original #411 resource change remains in #411. This design changes its bootstrap authority explicitly, not its substantive acceptance criteria.

## The bootstrap primitive

GitHub documents that a `push` workflow can run before that workflow has been merged into the default branch. The pushed commit supplies its workflow version. Therefore two distinct, previously unused activation branches can both point at exactly the approved root `T`: one starts source execution; a later push starts a separate publisher. Neither requires P to have merged. A new `workflow_run` publisher would require its file on main first and is not used for bootstrap. [GitHub push and workflow_run events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push).

Use a normal authorized Git push of T to an absent non-main ref, with an explicit empty-ref lease. Do not depend on an unspecified event from a REST ref-creation call. Use an existing authorized user/App credential; never place that credential in a producer. A repository `GITHUB_TOKEN` push normally does not start another push workflow. [GitHub trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

Proposed workflow files and names are distinct from the ordinary source and publisher:

- `.github/workflows/ci-policy-transition-source.yml`: `OFARM2 temporary policy source v1`; only `refs/heads/ofarm-ci-transition/source/<grant-id>`.
- `.github/workflows/ci-policy-transition-publication.yml`: `OFARM2 temporary policy publication v1`; only `refs/heads/ofarm-ci-transition/publisher/<grant-id>`.

The ordinary preparation branch is outside both filters. No schedule, dispatch, pull-request event, main trigger or broad fallback is added. Admission requires a new-ref push, the exact expected ref, repository, workflow path, workflow SHA and event SHA at T. An observed change or deletion of an activation ref revokes its use permanently. The immutable T/run binding, not an assertion of complete branch history, prevents replacement or recreation from authorizing another use. Rerun attempt 2 is forbidden. The ordinary main publisher must not subscribe to the new source name and must continue refusing its provenance.

Provider documentation establishes an executable pre-main route; it does not establish that our future implementation has run successfully. Credential eligibility, repository Actions policy, workflow registration, actual run identity and complete hosted results are installation gates, not assumptions to waive.

## Authority and threat model

| Owner or input | Authority and limits |
| --- | --- |
| Task user | Approves the named P decision; separately selects exact reviewed root T and its bounded consumer use; later retains each PR's exact-head merge decision. |
| Immutable T | Implements the approved transition only. It cannot approve itself, select a replacement root, widen its consumers or waive tests. |
| Original same-task approval and exact-root grant | External authority. Both must remain directly retrievable, in the required order. A receipt cannot manufacture this authority. |
| Delegated coordinator/operator | Validates the original messages, freezes T, maintains the single-use journal, makes approved non-main pushes and technical binding comments, and runs the independent final-packet verifier. No extra merge authority. |
| GitHub API and Actions | Authoritative run, ref, PR, comment, artifact and merge facts, subject to fresh validation. Unknown or inaccessible facts refuse. |
| Candidate merge and its artifacts | Untrusted code/data. Only isolated producer jobs execute candidate code. No candidate value chooses the trusted root or a privileged cancellation target. |
| Existing substantive policy at trusted base B | Owns baseline validation, comparison, safe extraction, source authentication and native evidence checks. These rules are preserved. |
| Transition external consumer | Authenticates the complete chain against externally supplied T and the original grant before a final packet can use the evidence. No inference from names or `passed` flags. |

Protected assets are honest, current, complete evidence; the separation between candidate execution and authoritative publication; finite runner resources; the user's approval authority; and native merge authority. The primary risk is allowing candidate-controlled or replayed policy to authorize its own evidence. Containment is external root selection, an immutable policy closure, exact single-use run binding, independent publication, current-state checks and complete substantive validation.

The attacker may control candidate files, tests, artifacts and ordinary comments; race or mutate untrusted data; supply hostile archives; and try stale or foreign evidence. Compromise of the task user's original messages, the delegated operator's isolated environment/credential, GitHub, trusted Actions or the approved root itself is outside this provisional model, as compromise of main policy is outside the existing one. Repository standing alone is not semantic approval. An authorized standing reviewer may revoke work, but cannot replace T through a revocation or admission comment.

**New reliance:** T is selected after complete implementation, mandatory/cheap checks, all focused transition controls and exact-head independent review, but before P has its own complete hosted acceptance. This is the bootstrap trust decision, not a claim that P already passed. #413 and #411 do not contain P's added tests and their runs cannot validate those tests. P still cannot merge until its own full normal evidence exists. If the user does not accept this provisional root-selection reliance, this route must not activate; the existing 45-minute block remains.

This remains pre-deployment repository authority. It does not supply independently human-controlled production approval/signing or authorize production access. No new signing system is introduced in this PR.

## Implementation shape and frozen policy closure

P is based on the then-current trusted main B. T is P's exact complete reviewed implementation commit, not a mutable branch alias or a receipt-selected SHA. T includes the ordinary base files, new transition modules/workflows/tests, source inventory additions and the narrow design/procedure amendment. It must have no unrelated changes. After any base or implementation change, freeze a new T, obtain the required fresh review and grant, and regenerate evidence; do not reassign an old grant.

Preserve the normal workflows and substantive verifier files byte-for-byte relative to B. In particular, do not change `conformance/run_review_baseline.py`, `conformance/evidence_publication_policy.py`, normal admission behavior, config/locks/schema, native verifier/release identity, original tests or frozen receipts. New transition admission code must use the actual transition event class; it must not forge `ISSUE_COMMENT_ADMISSION`, main refs, `workflow_run`, or `MAIN_PUSH` to reuse old public entry points.

Use a small transition adapter for provenance/grants and the existing substantive validation implementation. Reuse available low-level pure helpers without modifying their source. Do not factor or edit the ordinary admission module under this design: its pinned hash would force changes to ordinary workflows and currentness, contradicting the closed preservation promise. The new grant/comment schema needs its own narrow admission adapter and negative controls; it must not clone the substantive evidence validators. The current `_ensure_no_live_revocation` returns early for other event classes; calling it with a transition class is not protection. Transition live validation must explicitly perform the corresponding full checks.

To avoid maintaining a second handwritten evidence workload, generate the two transition workflow files deterministically from the canonical workflows at B using a small closed transform. The source of truth for existing producer and publisher operations remains B. Generation runs during preparation, never from candidate data in CI. Input blob/digest and every allowed rewrite are pinned. Unknown structure, missing/duplicate anchors or unlisted changes refuse generation. Commit the generated output for direct review; regeneration and parity checks must reproduce it exactly.

The transform is limited to event/name/ref filtering; transition admission and recheck invocations; T-only policy checkout/provenance; the conformance ceiling fixed to 60; new trusted guards; the versioned ticket/receipt adapter; and moving the final receipt seal to a fresh guarded job. It must preserve each substantive command, order, environment scrub, service setup/cleanup, test selection, artifact content, native matrix/build/verification and action/tool/image pin. It cannot add retries, continue-on-error, caches, filtering, widened success conditions or normalization. Exact command/step parity and explicit expected differences are required cheap checks. A refactor which cannot prove this parity is a design Blocker, not permission to copy-and-edit the workload freely.

Before T is frozen, its policy manifest pins the repository numeric ID and full name, one delegated operator's stable GitHub account ID, its fixed consumer PR number, and the campaign sunset. Never take the operator ID from a public projection or admission input. The actual push sender/run actor (and triggering actor where present) and the admission/source/publisher binding authors must match this pinned account by provider-authenticated numeric ID and still satisfy repository standing. Verify the API record against the job context, not just a login string. The future exact-root grant must select that same operator. An existing user/App credential is usable only if its real actor identity and comment standing satisfy these pins; otherwise preflight stops. A standing collaborator can revoke but cannot activate the expensive jobs or substitute a projection.

The new root closure binds the full T tree, B, input workflow blobs, generated workflows, adapter, external verifier, grant schema, new tests and every imported helper/config/tool pin. It separately records the unchanged ordinary native-currentness record and six authority files, and asserts that native substantive steps match their canonical source. The transition closure is additional CI provenance; it cannot relabel or expand the native release/currentness claim. If implementation needs to alter that accepted native-currentness contract, stop and propose its separate boundary before editing it. A full-tree digest alone is not a substitute for the declared executable dependency closure and parity proof.

Expected new areas: `conformance/ci_policy_transition.py`, a small generation/parity helper, `conformance/test_ci_policy_transition.py`, a root Kernel test bridge and generated inventory, the two named workflows, and a versioned transition RFC. Existing procedure navigation is in-boundary. Avoid a new generic CI framework, new dependency or cloned substantive validator. Exact filenames are scope predictions, not a closed approval file list.

## Grant, single-use state and revocation

Each exact-root packet fixes: decision/card/approval references; repository; P and T/full tree/closure digests; trusted B; one consumer PR and reviewed head H; exact current base B and GitHub execution merge M/parents; review identity; actual workflow paths/names and source/publisher refs; one unique grant ID; authorized operator identity; approved 60-minute envelope; fixed creation/expiry times; and the external verifier hash plus journal location, format version and immutable genesis hash. It permits at most one source attempt and one publisher attempt, both attempt 1. The grant expires after at most 24 hours and cannot extend beyond a fixed transition sunset written into the reviewed root (at most seven days after the first activation). The fixed sunset is chosen before freezing the first root, belongs to this one transition campaign and remains identical in T1; it is never reset by a new root or grant. Exact grant timestamps are filled only when implementation exists and must be visible before approval. No default or open-ended time is accepted.

The delegated operator maintains one durable monotonic grant journal outside all candidate workspaces, under a single-writer lock. Its immutable genesis fixes the prospective unique grant ID, technical coordinates and format before approval; the later activation packet pins this genesis digest, and the later original approval reference is appended afterward. The genesis cannot include a final grant digest which in turn contains the genesis digest. This ordering avoids a circular hash. Then each durably synced append has a sequence number and previous-record digest. The grant pins the genesis hash, not the changing tail. Truncated, broken or rolled-back records refuse against the separately retained last acknowledged tail; the operator must preserve that checkpoint outside the candidate as well. This is a trusted operator record, not an independently tamper-proof approval system. Journal states are `APPROVED -> SOURCE_RESERVED -> SOURCE_BOUND -> SOURCE_PASSED -> PUBLISHER_RESERVED -> PUBLISHER_BOUND -> SEALED -> ACCEPTED -> RETIRED`; failure, uncertainty, revocation or expiry is terminal. Intent is saved before each public write; actual immutable run/comment IDs and digests are appended after reconciliation. A lost response is reconciled by exact identity, never by resubmitting a fresh binding. No second operator is allowed for the same grant. Missing/ambiguous/lost journal state refuses; never rebuild unused authority from a GitHub comment list. This journal records consumption, not human approval, and cannot override the original grant.

Before source activation, create one immutable transition admission record on the consumer PR with a distinct marker (`OFARM2_CI_TRANSITION_ADMISSION_V1`), grant, T, B/H/M, review and exact body digest. Never create the ordinary baseline admission footer for this transition. The push starts only a cheap trusted gate. Within a fixed 5-minute window the operator observes the actual run identity, permanently binds the journal to that one run, and creates exactly one unedited `OFARM2_CI_TRANSITION_SOURCE_BINDING_V1` record naming that actual run/attempt. The publisher repeats this once with its own record plus exact source run and ticket ID/digest. It may not choose `latest successful`.

The gate requires complete bounded comment/history reads, unique matching records, exact IDs and digests, unchanged timestamps, no minimization, current repository standing, all creating/pushing actor IDs equal to the operator pinned inside T, and agreement with the frozen technical grant projection. Duplicate/edited/deleted/minimized/inconsistent records refuse; pagination gaps or unavailable state refuse. Later stages re-fetch the exact bound IDs. A previously bound grant is never rebound even if its comment/ref/run was deleted. A second push cannot use the retained binding because the run ID differs. External acceptance also checks the independent journal's first and only tuple. Branch names and concurrency are not one-use locks. Deletion followed by recreation cannot recover authority.

CI verifies the machine projection of the grant, not the original Codex user identity. The isolated trusted operator verifies and translates the original task-user grant before pushing; the external consumer verifies it again before accepting. This delegated provisional trust must be stated in the activation packet. A collaborator-created comment or a root-produced receipt cannot substitute for a missing original message.

For PR lifecycle history, read the complete bounded GitHub `timelineItems` connection from admission through the present, including Closed/Reopened, HeadRefDeleted/Restored/ForcePushed and BaseRefChanged/Deleted/ForcePushed events; record event IDs/cursors and timestamps, and refuse gaps, pagination excess or inconsistent reads. A return to an old head requires a force-push or ref restoration, so current equality alone is insufficient. This uses provider PR history, not the repository activity feed. [GitHub PR timeline types](https://docs.github.com/en/graphql/reference/pulls#headrefforcepushedevent). The generated workflow roots also fix one consumer PR number, allowing the source and publisher to use the existing `ofarm-pr-<number>` concurrency group; trusted main PR lifecycle events then provide the existing immediate cancellation path. The transition guards still handle their own marker changes and the gaps between runs.

Live validation covers original admission and all bindings/grant projection; exact ref-to-T identity; root expiry; current PR open/head/base/merge; close/reopen and head-change history, not only final values; user cancellation as translated immediately by the trusted operator; and standing reviewer revocation. Recognize the existing exact-head baseline revocation as a veto as well as a new transition-specific grant revocation. A transient close/reopen or head change which returns to H still revokes through PR history. For the two new activation refs, GitHub does not supply an equivalent complete ref-history proof here: recheck their current T and preserve every observed mismatch as terminal, but do not claim polling detects an unseen move-away-and-back. Such a move cannot change the already pinned workflow SHA or create a second accepted run because the journal and binding fix the first run ID. Add this adversarial case to the replay controls. Unverifiable required authoritative state fails closed.

Trusted guard jobs poll at most every 15 seconds, with bounded API requests and pagination. Guards run only T code on fresh runners. Only these jobs receive `actions: write` to cancel their own authenticated run ID; they receive no contents/issues/checks write and never execute candidate or downloaded code. This is a real new CI cancellation privilege, confined to the selected root. Producers, handoff, publication validators and seal remain read-only except for their existing artifact-upload capability. No secret, ID token, trigger credential, writable cache or shared workspace crosses from a privileged job to a producer.

Cancellation failure does not authorize success: the guard fails, preventing a valid handoff or final seal even if another job finishes. Polling is not instantaneous and an API read is not atomic with native merge. Preserve fresh checks at each decisive stage and the ordinary native expected-head condition; never claim an atomic GitHub comment/merge transaction.

## Execution and publication state machine

Source DAG:

```text
external grant + reviewed T + created admission
  -> source push -> 5m trusted binding gate
  -> [conformance60; native-amd64(120m); native-arm64(120m)]
       \ trusted source guard observes all three until terminal
  -> successful producers AND successful guard
  -> fresh T-only handoff(10m), final live checks, ticket uploaded last
  -> successful exact source run
```

Guard timeout is 135 minutes, bounded by the 24-hour grant and seven-day sunset. It waits for the entire expected producer set; absent, skipped, failed or cancelled producers cannot count as success. It ends only after those producers finish and a final live check. Handoff depends on guard success and rechecks at start and immediately before ticket upload. No guard waits for a handoff that itself waits for the guard. The ordinary main cancellation path may supplement this, but transition safety does not depend on it recognizing new comments.

The conformance job executes the original two full baseline commands sequentially in fresh subprocesses on the same runner and same three freshly provisioned clusters, followed by the original fixed comparison and 23-case platform lane. The actual PostgreSQL system identifiers and runner image version remain comparison inputs. Both native architecture jobs retain their existing complete builds, sanitizers, attestation, reproducibility and authentication checks. All pins and other existing timeouts remain unchanged.

Source artifacts remain exactly `conformance-provisional`, `native-verifier-amd64-provisional`, `native-verifier-arm64-provisional`, plus a new `ci-policy-transition-ticket-v1` uploaded only by the fresh handoff. No per-baseline, guard, debug or coordination artifacts are added to this closed inventory. Job outputs may convey bounded typed metadata, never scripts/expressions or executable downloaded input. Ticket binds real source identity, T, grant/admission/bindings, B/H/M, and all three provisional IDs/digests. Pre-squatting and missing/extra artifacts refuse. Phase ownership is enforced by the trusted DAG, isolated handoff/seal code, upload output IDs and pre-upload inventory checks; the artifact API alone is not proof of which job uploaded a file. The ticket must not exist before the trusted handoff creates it, and no producer remains running at that point.

Publisher DAG:

```text
successful source + exact ticket + unspent publisher slot
  -> separate publisher push at the identical T
  -> 5m trusted publisher-binding gate / source admission
  -> fresh validation/publication job(45m)
       \ trusted publisher guard observes validation until terminal
  -> successful validation AND successful guard
  -> fresh T-only seal(10m), live rechecks, transition receipt uploaded last
  -> successful exact publisher run -> external acceptance verifier
```

Publisher guard timeout is 60 minutes and cannot outlive the grant. Source-admission work keeps its existing maximum 10 minutes after binding. The guard observes the validation job, not the seal, to avoid a cycle. The seal re-resolves the exact successful source and five published artifacts, and rechecks all live bindings before uploading the receipt. The new guard/binding/seal overhead is finite and named; it does not increase any substantive test timeout other than the explicitly selected conformance60 envelope.

The publisher runs only T on fresh runners, never the admitted merge. It uses the existing bounded authenticated source reader and exact Git blob proofs. It downloads exact artifact IDs, checks digests before extraction, refuses traversal/links/special files/duplicates/size excess and enforces exact inventories before and after metadata. It independently reconstructs comparison using the unchanged fixed four-pointer normalization; it re-authenticates both native artifacts and derives the native index only from those authenticated results. Preserve Git configuration/hook/fsmonitor isolation and policy reauthentication after downloads.

Keep the five existing evidence artifact labels/content contracts; their authority comes from the new explicit receipt, not their names. The final artifact is `ci-policy-transition-publication-receipt-v1`, with schema `ofarm.ci-policy-transition-publication.v1`. It binds the real push source and publisher refs, T and workflow closure, distinct run IDs/attempt1, exact grant/admission/binding IDs/digests, B/H/M, all four source IDs/digests and all five published evidence IDs/digests. No ordinary main receipt is minted. Failure after any upload leaves untrusted incomplete artifacts.

## External recognition and native acceptance

The consumer is an approved verifier run in a fresh isolated local checkout of T, with original grant and expected T supplied out-of-band by the trusted operator. It cannot choose T from a receipt or import anything from the candidate. It reauthenticates T and the closure, the original approval/grant ordering, unspent/unique journal tuple, live provider identities, comments/history/revocation, successful distinct runs, ticket, closed artifacts and full data validation. Complete downloads and substantive validators are reused from T; a receipt's `passed` field is not sufficient.

The technical verifier can validate a signed-off machine projection, but the coordinator must independently retrieve and verify the original same-task user messages. Both results are required in the final packet. Missing original authority refuses even if every byte digest passes. The grant authorizes one final acceptance use; record acceptance once with the bound tuple. A repeated read is idempotent inspection of that same consumed tuple, never a new admission or a grant for a new candidate.

The retained verifier has two explicit result purposes. `verify-for-acceptance` requires all live facts above and can feed only the named current final packet. `audit-consumed` examines an already consumed historical tuple, archived raw artifact bytes, root/closure, original authority references, recorded acceptance and native merge. It reports archive integrity and which provider facts can still be re-authenticated, with missing/expired sources explicitly unavailable. It does not require the PR still be open or refs still exist, and it can never grant new execution, live acceptance or merge authority. Before retiring refs, create a Git bundle containing each exact T/T1 and its closure/base dependencies in the isolated audit archive, verify the bundle and re-fetch it into an empty repository to confirm the expected commit/tree, and record its digest. Preserve that bundle, complete raw archives and their receipt-bound hashes, provider identity snapshots and original-message references outside candidate workspaces; do not describe an offline copy as a fresh authenticated provider read. This bounded historical verifier is the useful retained outcome of P after active workflow removal.

Only after every gate succeeds may the normal complete final packet be presented. The user later authorizes that consumer PR at its exact current head. Immediately before native merge, repeat live scope/head/base/currentness/admission/receipt/cancellation/protection checks. Use expected-head native PR merge only. No admin merge, status forgery, direct-main write, protection removal or old evidence substitution is permitted. Native rejection stops. If the base changes, fresh evidence is required; the old grant does not follow it.

Deleting active temporary machinery is part of the approved P lifecycle, not a new capability. Removing it changes the head and requires fresh checks/review/full acceptance as usual. Do not keep an unbounded dormant fallback on main.

No grant may be repaired in place. Unknown push outcome is reconciled before any continuation; refusal/failure consumes the attempt. A new use after diagnosis requires a new exact-root packet and user grant, with no automatic renewal or retry. A newly discovered independent runtime, DB, native-currentness or publication-custody change stops implementation at that boundary and becomes separate Delivery work.
