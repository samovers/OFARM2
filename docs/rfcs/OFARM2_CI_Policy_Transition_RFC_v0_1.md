## The bootstrap primitive

GitHub documents that a `push` workflow can run before that workflow has been merged into the default branch. The pushed commit supplies its workflow version. Therefore two distinct, previously unused activation branches can both point at exactly the approved root `T`: one starts source execution; a later push starts a separate publisher. Neither requires P to have merged. A new `workflow_run` publisher would require its file on main first and is not used for bootstrap. [GitHub push and workflow_run events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push).

Use a normal authorized Git push of T to an absent non-main ref, with an explicit empty-ref lease. Do not depend on an unspecified event from a REST ref-creation call. Use an existing authorized user/App credential; never place that credential in a producer. A repository `GITHUB_TOKEN` push normally does not start another push workflow. [GitHub trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

Proposed workflow files and names are distinct from the ordinary source and publisher:

- `.github/workflows/ci-policy-transition-source.yml`: `OFARM2 temporary policy source v1`; only `refs/heads/ofarm-ci-transition/source/<grant-id>`.
- `.github/workflows/ci-policy-transition-publication.yml`: `OFARM2 temporary policy publication v1`; only `refs/heads/ofarm-ci-transition/publisher/<grant-id>`.

The ordinary preparation branch is outside both filters. No schedule, dispatch, pull-request event, main trigger or broad fallback is added. Admission requires a new-ref push, the exact expected ref, repository, workflow path, workflow SHA and event SHA at T. An observed change or deletion of an activation ref revokes its use permanently. The immutable T/run binding, not an assertion of complete branch history, prevents replacement or recreation from authorizing another use. Rerun attempt 2 is forbidden. The ordinary main publisher must not subscribe to the new source name and must continue refusing its provenance.

Provider documentation establishes an executable pre-main route; it does not establish that our future implementation has run successfully. Credential eligibility, repository Actions policy, workflow registration, actual run identity and complete hosted results are installation gates, not assumptions to waive.

Each exact-root packet fixes: decision/card/approval references; repository; P and T/full tree/closure and coverage-declaration digests; trusted B; one consumer PR and reviewed head H; exact current base B and GitHub execution merge M/parents; review identity; actual workflow paths/names and source/publisher refs; one unique grant ID; authorized operator identity; approved 60-minute envelope; fixed creation/expiry times; and the external verifier hash plus journal location, format version and immutable genesis hash. It permits at most one source attempt and one publisher attempt, both attempt 1. The grant expires after at most 24 hours and cannot extend beyond a fixed transition sunset written into the reviewed root (at most seven days after the first activation). The fixed sunset is chosen before freezing the first root, belongs to this one transition campaign and remains identical in T1; it is never reset by a new root or grant. Exact grant timestamps are filled only when implementation exists and must be visible before approval. No default or open-ended time is accepted.

The delegated operator maintains one durable monotonic grant journal outside all candidate workspaces, under a single-writer lock. Its immutable genesis fixes the prospective unique grant ID, technical coordinates and format before approval; the later activation packet pins this genesis digest, and the later original approval reference is appended afterward. The genesis cannot include a final grant digest which in turn contains the genesis digest. This ordering avoids a circular hash. Then each durably synced append has a sequence number and previous-record digest. The grant pins the genesis hash, not the changing tail. Truncated, broken or rolled-back records refuse against the separately retained last acknowledged tail; the operator must preserve that checkpoint outside the candidate as well. This is a trusted operator record, not an independently tamper-proof approval system. Journal states are `APPROVED -> SOURCE_RESERVED -> SOURCE_BOUND -> SOURCE_PASSED -> PUBLISHER_RESERVED -> PUBLISHER_BOUND -> SEALED -> ACCEPTED -> RETIRED`; failure, uncertainty, revocation or expiry is terminal. Intent is saved before each public write; actual immutable run/comment IDs and digests are appended after reconciliation. A lost response is reconciled by exact identity, never by resubmitting a fresh binding. No second operator is allowed for the same grant. Missing/ambiguous/lost journal state refuses; never rebuild unused authority from a GitHub comment list. This journal records consumption, not human approval, and cannot override the original grant.

Before source activation, create one immutable transition admission record on the consumer PR with a distinct marker (`OFARM2_CI_TRANSITION_ADMISSION_V1`), grant, T, B/H/M, review and exact body digest. Never create the ordinary baseline admission footer for this transition. The push starts only a cheap trusted gate. Within a fixed 5-minute window the operator observes the actual run identity, permanently binds the journal to that one run, and creates exactly one unedited `OFARM2_CI_TRANSITION_SOURCE_BINDING_V1` record naming that actual run/attempt. The publisher repeats this once with its own record plus exact source run and ticket ID/digest. It may not choose `latest successful`.

The gate requires complete bounded comment/history reads, unique matching records, exact IDs and digests, unchanged timestamps, no minimization, current repository standing, all creating/pushing actor IDs equal to the operator pinned inside T, and agreement with the frozen technical grant projection. Duplicate/edited/deleted/minimized/inconsistent records refuse; pagination gaps or unavailable state refuse. Later stages re-fetch the exact bound IDs. A previously bound grant is never rebound even if its comment/ref/run was deleted. A second push cannot use the retained binding because the run ID differs. External acceptance also checks the independent journal's first and only tuple. Branch names and concurrency are not one-use locks. Deletion followed by recreation cannot recover authority.

The isolated trusted operator verifies and translates the original task-user grant before pushing; the external consumer verifies it again before accepting. This delegated provisional trust must be stated in the activation packet. A collaborator-created comment or a root-produced receipt cannot substitute for a missing original message.

Only an empty complete first page with filtered count zero can pass; every returned lifecycle event revokes immediately, and an empty page advertising more pages refuses. Guards receive no contents/issues/checks write and never execute candidate or downloaded code. Producers, handoff, publication validators and seal remain read-only except for their existing artifact-upload capability. No secret, ID token, trigger credential, writable cache or shared workspace crosses from a privileged job to a producer.

Cancellation failure does not authorize success: the guard fails, preventing a valid handoff or final seal even if another job finishes. Polling is not instantaneous and an API read is not atomic with native merge. ## Protected API requests and observation delay

Review B1 demonstrated that the old 15-second design could spend at least 2,160 REST requests per hour on guard polls alone. GitHub documents separate `GITHUB_TOKEN` limits of 1,000 REST requests and 1,000 GraphQL points per hour per repository for this non-enterprise case. This revision uses neither a larger credential allowance nor an assumed conditional-request hit rate. [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-github_token-in-github-actions); [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#primary-rate-limit).

**One cadence:** periodic full sweeps start on one grant-wide UTC grid at 120-second intervals. Source and publisher guards never overlap. The same grid continues across their handoff; starting a job does not reset it. Immediate admission, guard-start, guard-final and decisive-stage checks remain mandatory and are charged to the nonperiodic allowance below. A complete sweep has a 15-second wall-clock deadline covering all requests, pagination and parsing, not a separate 15 seconds per request. A missed scheduled sweep or exceeded deadline fails the guard; there is no catch-up burst, skipped required fact or success from an older snapshot. Reaching expiry is checked locally without waiting for a sweep.

The maximum scheduled detection delay is 135 seconds (120 until the next tick plus 15 to complete or fail), followed by GitHub's cancellation-delivery latency. This replaces the unapproved 15-second cadence explicitly; it is not instantaneous revocation. Existing ordinary PR concurrency cancellation still supplements it. Fresh complete checks immediately before each decisive handoff, publication, seal, external acceptance and native merge preserve refusal of revoked or stale authority even inside that observation window. No substantive test, assertion, complete-baseline requirement or final acceptance check is removed or deferred until after merge.

A periodic sweep permits at most **15 REST requests and 5 GraphQL points**, counting every page and response. The largest normal publisher observation set is explicit:

Every protected request is charged conservatively, including a conditional request; this design needs no ETag cache or assumed 304 rate. The 990/430 total is a protected-operation planning envelope including margin, not a verified bound on the entire workload or provider. A later stage rechecks available headroom and actual returned cost before proceeding. Unknown, contradictory or insufficient required quota state, protected pool overrun, a protected `403`/`429`, protected GraphQL errors or incomplete required data (including HTTP 200), primary/secondary throttling of a protected operation, incomplete scan or deadline failure refuses the attempt without ticket/receipt authority. A fresh remaining/reset response is a snapshot, not a reservation or an attributable traffic ledger. Subtracting snapshots cannot identify hidden callers. The remaining schedule excludes a periodic tick only after this isolated guard completes its full live and producer-state sweep in its own current periodic pool. At an exact tick boundary that completed sweep is already charged, so it is not future work. Initial checks and unproven ticks earn no such exclusion. Primary reset timestamps need not arrive in increasing order. Each independently
expiring observation remains a constraint in the same trusted accounting ledger;
a changed reset or higher remaining value cannot replenish or erase a live one.
REST responses require resource `core`; existing tool resource checks and the
GraphQL document/cost checks remain mandatory. Missing facts, changed limits,
expired observations and insufficient headroom still refuse.

Before dispatch, associate the request with local bucket cost `S` already known
complete, excluding every pending request. An observation of remaining `r` at
expiry `e` records capacity `C = r + S`. Its balance at a later check is `C - U`,
where `U` is all locally charged cost in that bucket. Thus observing, concurrent
and later work cannot receive false completion credit; double counting the
observing request is conservative. Same-expiry observations coalesce by minimum
capacity. Every live expiry must separately support the unchanged remaining
stage/sibling allowances, scheduled sweeps through its own expiry, and75/75
margin. A shorter new expiry cannot shorten an older live forecast.

An old constraint retires only on a valid response to an already-required request
whose trusted start time is at or after that constraint's expiry. Clock passage
alone supplies no renewal, and a request begun before expiry supplies none even
if it finishes afterward. The clock cannot move backward. Existing2048-request,
trace and ledger byte bounds cap state; overflow refuses without evicting live
constraints. Raw last observations remain separate solely for the unchanged
same-window GraphQL cost proof; an aggregate cannot prove an unknown query cost.
This is a version4 implementation correction preserving required quota
sufficiency, not an added traffic exception, quota reservation, wait or retry.
